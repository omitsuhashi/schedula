# 設計方針

## この文書の位置付け

元チャットの利用目的と最後に示された開発順序、および ZIP の具体的な契約を、
schedula の実装方針として採用する。変更を判断するときの基準をまとめる。
由来は[出典と採用判断](sources.md)、フィールドの意味は[入出力契約](io-contract.md)を参照する。

## JSON 契約を中核に置く

入力と出力にバージョン付き JSON 契約を持ち、LLM なしで検証・実行できるようにする。
人、技能、役割、需要、ルール、目的は ID で参照し、`label` は表示用に限定する。
同じ条件なら、手書き JSON、フォーム、CSV、将来の LLM のどの経路でも同じ意味になる。
中核の公開境界は Request → Response とし、DB、認証、Web、プロバイダー固有形式は
その外側で扱う。[ADR-0001](adr/0001-json-first-engine.md)

JSON Schema は構造の正本とし、ID の存在、時間の整合、対応モードなどの意味検証を併用する。
未知フィールド、未知ルール、不正参照、非有限数、時間粒度のずれを拒否する。
未知プロパティの拒否には `additionalProperties: false` を使う。
この機能の意味は [JSON Schema の公式説明](https://json-schema.org/understanding-json-schema/reference/object)に対応する。
スキーマだけで現場のルールや情報の真偽まで検証できるとは扱わない。

## 問題の構造からソルバーを選ぶ

通常の指定は `solver.backend: "auto"` とする。
`auto` は、一つの Request に対して対応するバックエンドを一つ選び、一つの解を返す。
複数バックエンドを競わせる処理や、異なる複数案の生成・選択は初期設計に含めない。
CP-SAT では目的順序に沿って同じバックエンドを複数回呼び出す場合があるが、
これは優先順の最適化であり、複数方式の比較や別案の生成ではない。

| 問題の構造 | 選択 |
| --- | --- |
| `assignment`、明示制約なし、目的は空または割当ごとの `preference_penalty` | `min_cost_flow` |
| `assignment` に担当時間上限、担当切替の制約・目的がある | `cp_sat` |
| `roster` | `cp_sat` |

0.1 参照実装の `choose_backend` は、`constraints` が非空なら CP-SAT を選ぶ。
条件を分析してさらに最小費用流へ振り分ける改良は、同値性を検証してから行う。
明示指定された方式が条件に対応できない場合は `INVALID_INPUT` を返し、条件を捨てない。
必要な依存がなければ `BACKEND_UNAVAILABLE` を返し、制約を減らした方式へ自動退避しない。

最小費用流の適用範囲には制限があることは
[OR-Tools の割当の説明](https://developers.google.com/optimization/flow/assignment_min_cost_flow)に沿う。
勤務の整数・論理制約を扱う CP-SAT の出発点には
[従業員スケジューリングの公式例](https://developers.google.com/optimization/scheduling/employee_scheduling)を用いる。
この分け方は初期方式の選択であり、schedula の実務規模で最速と確認した結論ではない。

## 勤務と担当を同時に決める

`roster` では、勤務候補を選ぶ変数と、その勤務中に役割を担当する変数を同じモデルに置く。
出勤人数を先に固定する方式では、人数が足りても技能が不足する場合があるためである。
選ばれた勤務の休憩を除く時間だけ担当可能とし、勤務中の未担当時間は待機として扱う。
[ADR-0002](adr/0002-joint-roster-optimization.md)

## 必須条件・選好・目的順序を分ける

需要、担当資格、勤務可能時間、二重配置の禁止、指定された `constraints` を必須条件とする。
解がないときも無断で緩和しない。将来の不足・緩和提案は、正式な解と別の結果として設計し、
利用者が条件を変更した Request を確定してから再計算する。

「技能者の皿洗いをなるべく避ける」は `preferences` の `avoid_role` として表し、
人数を満たすため必要なら担当を認める。役割の必要技能は AND 条件とする。
未登録の技能をレベル0として担当資格ありにしない。

`objectives` の配列順を辞書式の優先順とする。すべての初期指標は小さい方をよい評価とする。
上位目的の最適性を証明してからその値を固定し、次の目的を解く。
上位目的が `FEASIBLE` にとどまればそこで終了し、後の目的を優先し直さない。
巨大な重みを暗黙に付けて優先順位を表現しない。

## 候補展開はプログラムで行う

勤務の出退勤・休憩は有限候補方式で始める。
利用者は明示的な `shift_candidates`、または短い `shift_templates` を入力する。
候補集合や時間枠の0/1行列を LLM に大量列挙させず、エンジンが決定的に展開する。

例では4人 × 2日 × 出勤時刻1通り × 勤務長1通り × 休憩位置4通りで32候補を作る。
計画期間・勤務可能時間に収まらないテンプレート由来の候補は除外する。
明示候補が勤務可能時間を外れる場合は入力エラーとする。
どちらの場合も勤務可能時間そのものを広げない。

`OPTIMAL` は指定の時間粒度、生成・入力された候補集合、必須条件、目的順序に対する最適性である。
候補外の出退勤・休憩や、未入力の現場ルールまで比較した意味にはしない。

## 結果を独立した処理で検証する

ソルバーのモデル構築とは別の処理で、結果の構造、担当資格、勤務可能時間、需要、
二重配置、選ばれた勤務・休憩、指定ルールを照合する。
ソルバーの変数値だけを信用せず、共通の解形式から評価値を計算する。
独立検証器はソルバーに依存させない。共有する日時・ID の処理には別途境界テストを置く。

検証に失敗した解は `solution` に出さず、`INTERNAL_ERROR` と診断を返す。
未検証の `verification.valid` は `null` とし、`true` にしない。
制約の追加時は、モデルだけでなく意味検証・結果検証・違反検出テストも更新する。

## 状態と説明根拠を保持する

最適解、実行可能解、不可能性の証明、未確定、入力エラー、依存不足、内部障害を分ける。
`UNKNOWN` を「実行不可能」と説明しない。この区別は
[CP-SAT の状態定義](https://developers.google.com/optimization/cp/cp_solver)を参考に、共通 Response へ適用する。
目的ごとの数値と `proven_optimal` を保持し、証明できた範囲を示す。

説明の根拠は `code`、`json_pointer`、`related_ids`、`facts` とする。
`message` は補助説明で、プログラムの分岐は診断コードを使う。
CP-SAT の詳細な矛盾原因は0.1では未実装であり、全体的な `NO_FEASIBLE_PLAN` から
唯一の原因や最低追加人数を推測して断定しない。

## LLM は確定前の入力候補と根拠に基づく説明を担う

自然言語から直接ソルバーへ進めず、RequestDraft を経由する。
Draft は未解決項目、仮定、根拠の入力文、参照したマスターの版を保持する方向とする。
Draft のフィールド構成と確認方法は別途設計し、0.1 Request に未定義の項目を追加しない。
勤務資格、需要人数、契約条件、履歴が未解決なら実行用 Request に昇格させない。

LLM が生成するものは列挙されたルールの型付きデータに限定する。
自由な Python、数式文字列、ソルバー制約コードを実行しない。
既知の人員・技能・資格・契約を無断で追加・変更しない。
`label`、入力文、添付文書の指示表現はデータとして扱う。

結果説明は返された評価値・診断に基づく。原因や資格を補作しない。
LLM プロバイダーの構造化出力への変換は外側のアダプターで行い、
ドメインの JSON Schema をプロバイダー固有の都合で直接変更しない。

## 性能と実行境界を検証可能にする

探索時間の予算と、入力検証・候補展開・モデル構築・結果検証を含む応答時間を分けて測る。
参照実装の `time_limit_seconds` は探索予算であり、外部応答期限ではない。
公開 API には別途、入力上限、プロセス隔離、キャンセル、応答期限を設計する。

比較では同じ入力、候補集合、目的順序、計算予算と共通検証器を使う。
seed だけで全環境の同率解・時間切れ結果が完全再現されるとは扱わない。
エンジン・ライブラリ版と入力条件を記録して、解の有効性と評価を比較する。
保存済みの架空入力と `scripts/evaluate.py` による時間・ピーク RSS の測定を
[実行評価](evaluations/runtime.md)に記録する。人数・期間は実務規模未確定のため提案値とし、
単発の測定値から性能保証や最速方式を決めない。
LNS や学習による探索改善は、この比較基準ができてから検討する。
