# 不可能性の矛盾条件を絞り込む契約

[#68](https://github.com/omitsuhashi/schedula/issues/68)で採用した設計を、[#76](https://github.com/omitsuhashi/schedula/issues/76)で[契約0.8](../diagnosis.md#契約08の条件グループ縮小)へ実装した。
旧版の `conflict.conditions` は全必須条件を返し、`validate_result` も全件一致を要求する。
契約0.8では背景条件Bと削除できる条件集合Gを分け、Bを保持した十分集合C⊆Gを返す。
元の `INFEASIBLE`・解なしと、既存 `allowed_changes` の許可範囲は変えない。

## 条件の分類

| 対象 | 初回の単位・扱い | 除去の意味 |
| --- | --- | --- |
| 需要 | 需要1件・区間全体を1グループ | その需要の人数条件だけを外す。担当変数・役割・候補は残す |
| `constraints` | 1件を対象従業員全員分で1グループ | 休息、連勤、期間上下限等、そのルールの式すべてを外す。上下限は同じ1グループ |
| `fixed_parts` | 明示固定1件を1グループ | 指定した勤務・役割状態の固定だけを外す |
| `preserve_assigned` | 自動固定全体を1グループ | 比較元の担当済み枠固定を外す。基準そのものは残す |
| 資格・技能・勤務可能時間・候補集合 | 背景 | 対応する変数がそもそも存在しない場合もある。無資格者や未知候補は作らない |
| 1人1枠1担当・勤務との結合・1人1勤務日・勤務外側区間非重複 | 背景 | 診断でも違反解を許さない |
| 時間枠、区間、ID、実績、#67の確定勤務、元基準の検証 | 背景 | 固定入力事実。診断目的で過去実績や確定勤務を変更しない |
| 目的、選好、目標 | 診断の実行可能性判定には不使用 | 必須条件ではない。元入力や正式な再求解からは削除しない |

需要除去はRequestの需要行を削除する操作とは異なる。
現行の「未指定需要は0」として再正規化すると、許される解が単調に増えなくなるためである。
元入力を一度正規化した同じ変数領域で、該当需要の等式・上限だけを構築しない。
グループ外の需要と未指定時間帯の需要0は維持する。
この診断用モデルは正式な勤務計画のモデルではなく、得た緩和解を `solution` や変更案へ載せない。

0.2では需要は完全充足条件。新契約は0.3以降の意味を継承するため、需要は過剰配置禁止の上限となる。
不足を許すグループの除去で「完全充足不能」を調べたとは扱わない。
元結果が `PARTIAL` なら `NOT_APPLICABLE / ORIGINAL_PARTIAL` のままとする。
0.2の解釈は比較試験に使い、旧版へ新しい診断フィールドを追加しない。

## 方式の比較と採用

[OR-Tools公式例](https://github.com/google/or-tools/blob/stable/ortools/sat/samples/assumptions_sample_sat.py)には
仮定リテラルを付けた条件から不可能性の十分集合を得る入口がある。
これを使うだけで要素数最少の集合を得たとは扱わない。

| 方式 | 長所 | この実装での費用 |
| --- | --- | --- |
| 仮定リテラルによるcore抽出 | 1回の探索で小さい十分集合を得られる場合がある | 全グループの式に切替リテラルを接続する必要がある。抽出後も独立な再構築と極小性の確認が必要 |
| 条件を除いたモデルの再構築・再求解 | 既存のルール構築を単位ごとに省略でき、十分性を再確認しやすい | 初期再確認1回、削除試行最大G回、最終確認1回。モデル構築も追加予算を使う |

初回は削除方式を採用する。条件IDの昇順で一度ずつ試し、並列化・全原因列挙・最少件数探索を入れない。
仮定方式は、同じ十分性を維持したまま実測のモデル構築時間が支配的になり、
対象制約の切替と最終独立再確認を検証できたときに初期集合の縮小へ導入する。
固定版9.15.6755の小規模検算では両方式で十分集合を得た。
`add_no_overlap` の仮定付き有効化・無効化も動作したため、未対応を採用理由にはしない。
実際の全ルールの仮定化を先に整備せず、構築の省略と再確認を一つの内部経路で扱うための選択である。

## 縮小と証明

1. 元の通常求解が `INFEASIBLE` の場合だけ実行する。
2. 新しく作った診断モデルでB∧Gを再確認する。`INFEASIBLE` ならC=Gを保存する。
   `UNKNOWN` なら縮小結果を返さない。実行可能ならモデル不一致として診断だけ `ERROR`。
3. 各gについてB∧(C−{g})を解く。`INFEASIBLE` ならgを除き、その証明を保存する。
   `FEASIBLE` / `OPTIMAL` なら緩和解を独立検証してgを残す。`UNKNOWN` はgを残し未確定として記録する。
4. 最後に別に再構築したB∧Cを求解し、十分性を再確認する。
   最終確認が間に合わなければ最後に証明したCを返し、`rechecked=false` とする。
5. Cの全要素の除去について、独立検証した実行可能証拠がある場合のみ `inclusion_minimal`。
   一つでも未確定なら `not_proven`。要素数最少や唯一の原因とは主張しない。

除去した制約を後で足し戻さないので、以前に得た除去時の実行可能証拠は後の小さい集合にも有効。
最終集合に対して証拠を再評価し、背景・残したグループすべてを満たすことを確認する。
Cが空でもBだけで不可能なら有効な背景矛盾であり、`background_only=true` を返す。
極小性は「Bを変えない、定義したグループ単位」に限定する。

`INFEASIBLE` と `UNKNOWN` の区別は
[CP-SATの状態定義](https://developers.google.com/optimization/cp/cp_solver)に従う。
不可能性の独立確認は別モデルによる再求解であり、ソルバー不要の検証器が不可能性を証明するとは説明しない。
`verify` が独立に検査できるのは、除去後の実行可能な勤務・担当の証拠である。
診断内の検証器は元JSONからBと有効グループを読む専用の内部経路を使い、通常 `verify` の条件を弱めない。

## 追加予算と返却契約

既存 `diagnosis` に `conflict_refinement: {time_limit_seconds: ...}` を追加する。
値は0超かつ既存の診断全体予算以下、診断全体は従来の最大300秒。
省略時は既存の全条件十分集合。指定時の縮小予算は全体予算に内包し、二重に足さない。
縮小→許可変更案の順に実行する。変更案用時間を確保したい呼出側は縮小予算を短く指定する。
各開始前に `min(全体の残り, 縮小の残り)` を計算し、構築・探索・検証・最終確認に使う。
構築・検証途中の強制中断は保証せず、外部期限は#65のプロセス実行管理に委ねる。
期限後に完成した縮小・提案は採用しない。元結果と予算内に完成した証拠を保持する。

新版の `conflict` は次の項目を持つ。

| 項目 | 意味 |
| --- | --- |
| `conditions` | Cの各要素。`group_id`、`code`、`json_pointer`、`related_ids`、`interval` |
| `background_conditions` | Bの参照一覧。同じ参照項目を使い、空候補集合も明記 |
| `infeasibility_proven` | 保存したCの不可能性が証明済みの場合のみtrue |
| `minimality` | `not_proven` / `inclusion_minimal` |
| `minimality_scope` | `condition_groups_relative_to_background` |
| `background_only` | Cが空か。原因がないことを意味しない |
| `rechecked` | 最終集合を新規モデルで再確認済みか |
| `checks` | 試した集合のgroup ID、除去対象IDまたはnull、状態、実行可能証拠の検証成否、経過秒 |

`group_id` は元のJSON pointerから決定的に作り、配列の再配置後には再生成する。
需要のintervalはその区間、期間上下限は指定区間、休息・連勤・全体上限は計画期間、
固定は固定区間。背景の候補には原区間を保持する。元入力にない代表時刻を原因として作らない。
再実行には元Request、エンジン・OR-Tools版、solver設定、返却group IDを保存する。
checksは監査記録であり、外部から渡された記録だけで証明を信頼しない。
実行可能証拠は内部で保持・検証し、通常Responseへ大量の緩和解を載せない。

`status=TIME_LIMIT` でも十分集合は返せる。縮小部分の `not_proven` と
診断全体の処理完了は別で、全対象を試してUNKNOWNが残れば `COMPLETE` かつ `not_proven` もあり得る。
元が `UNKNOWN` / `PARTIAL` / 正常なら従来通り何も縮小しない。
診断だけの例外は `ERROR` とし、元 `INFEASIBLE` を変更しない。

## 小規模の具体例

従業員Alice、10月7日09:00〜10:00の60分候補A、勤務可能・有資格とする。
新版では需要は0〜1人、需要不足は許す。xは候補Aの選択。

| 条件 | 内容 |
| --- | --- |
| `minimum` | 09:00〜10:00の `scheduled_minutes_bounds.min_minutes=60`、x=1 |
| `maximum` | Aliceの `max_scheduled_minutes.limit_minutes=0`、x=0 |
| `irrelevant` | Aliceの `max_assigned_minutes.limit_minutes=120` |

元は `INFEASIBLE`。`irrelevant` を除ける。
`{minimum, maximum}` は十分で、minimum除去では勤務0分、maximum除去では勤務60分の証拠がある。
この二条件が背景に対して包含極小。需要0でも待機60分を選べるため同じ矛盾が成立する。

Bobの独立した60分候補Bに同じ上下限矛盾を追加すれば、
`{Aliceのminimum, maximum}` と `{Bobのminimum, maximum}` の異なる原因集合がある。
決めた削除順でどちらか一つを返せばよい。全原因を返したとはしない。

Aliceのmaximumを除いた試行だけが `UNKNOWN` の場合は、その要素を残し `not_proven`。
別の試行で残り集合の不可能性を証明できても、UNKNOWNを「除くと成立する」の証拠に使わない。

従業員1人・60分候補1件に需要2人、他の制約なしの新版入力は不足60人分の `PARTIAL`。
完全充足不能を理由にこの縮小を起動してはならない。
同じ入力の旧0.2は `INFEASIBLE` だが、その版の診断動作は従来通りに保つ。

## 実装と検証の順序

| 実装単位 | 検証 |
| --- | --- |
| 新版Schema・グループ分類 | 全必須条件がGかBに一度属する。pointer・ID・区間が元入力へ解決できる |
| モデル構築の内部引数 `active_groups` | 全件有効時は通常の実行可能集合と一致。需要除去で変数を消さず、緩和が単調になる |
| 削除探索と予算 | 上の小例を全探索とCP-SATで照合。UNKNOWN・期限・例外で元結果と十分性を保持 |
| 独立証拠検証とResponse検証 | 無効な緩和解、架空pointer、極小性の偽装、背景の欠落を拒否。既存の全件一致検査を版別に更新 |
| 変更案・結合回帰 | 許可外の技能追加・候補追加・固定解除は引き続き拒否。複数案を勝手に組み合わせない。PARTIALを起点にしない |

実測では削除回数、証明数、UNKNOWN数、準備・探索・検証時間、最終集合の大きさを記録する。
初回から最少件数の保証や実務サイズの時間保証を付けない。
