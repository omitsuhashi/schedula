# 明示した勤務費用の契約案

[#69](https://github.com/omitsuhashi/schedula/issues/69)の仕様案。
同じ不足・必須条件の下で勤務費用を比較する `scheduled_cost` を `roster` に追加する。
給与計算ではなく、利用者が指定した係数による計画評価である。

## 最小案の選択

| 方式 | 利点 | 制約 |
| --- | --- | --- |
| 整数の分単価と明示倍率 | 勤務区間から独立再計算でき、テンプレートや期間分割にも同じ式を使える | 候補によらない従業員ごとの単価に限定。日額や残業段階料金は表せない |
| 候補ごとの整数総額 | 日額や休憩課金など、利用側で計算した結果を渡せる | テンプレート展開後のIDごとの網羅が必要。月境界の配賦と二重計上回避の追加契約が必要 |

初回は整数の分単価を選ぶ。整数倍率を持たせ、時給が60で割り切れない場合も浮動小数を使わない。
候補総額・複数通貨換算・勤務日固定費・残業の累進費用は導入しない。

## 入力と意味検証

以下は新版Requestに加える部分の例で、現行契約には未対応。

```json
{
  "costs": {
    "currency": "JPY",
    "units_per_currency": 60,
    "employee_rates": [
      {"employee_id": "alice", "units_per_minute": 1800},
      {"employee_id": "bob", "units_per_minute": 2400}
    ]
  },
  "objectives": [{"id": "cost", "metric": "scheduled_cost"}]
}
```

`currency` は必須の大文字英字3文字の識別子、`units_per_currency` は1〜1,000,000の整数。
外部の通貨登録簿や為替を参照せず、指定通貨の1単位をいくつの費用単位で表すかを利用者が宣言する。
`units_per_minute` は0〜1,000,000,000の整数で、0は明示的な無費用を意味する。
bool・null・浮動小数・非有限値・負値を受理しない。

`costs` と `scheduled_cost` は対にして指定し、片方だけなら `INVALID_INPUT`。
`employee_rates` は候補を持たない人も含め登録従業員の集合と厳密一致を要求する。
未知ID、重複、欠落を拒否し、未指定を0にしない。
従業員別通貨・倍率は持たず、混在項目は未知プロパティとして拒否する。
テンプレート由来の候補も従業員の同じ係数を使い、生成IDを価格表へ列挙しない。

計算は `sum(employee_rate * scheduled_minutes_in_W)`。
勤務分数は待機を含み、休憩と分割間の非勤務は除く。休憩を有給扱いにするフラグは設けない。
課金対象がこの定義と異なる業務には、初回仕様で同じ費用を表せるとは説明しない。
期間別単価は初回未対応で、単価変更区間・夜勤割増・休日割増を推測しない。
期間ごとに別Requestへ分けると勤務選択が変わり得るため、同一期間の最適化の代用とはしない。

## 整数・端数・上限

上例のAliceは1時間1800通貨単位、17分では `1800*17=30600` 費用単位、
通貨表示は `30600/60=510`。時給1001、1分なら1001費用単位、通貨表示は正確な比 `1001/60`。
エンジン内で勤務ごと・従業員ごと・合計の丸めを行わない。
支払時の丸めや税・手当は利用側が別途処理し、表示丸めした数値を最適化へ戻さない。

全候補の `rate * minutes(candidate∩W)` と確定勤務のW内費用の保守的な和をPython整数で計算する。
係数・集計の上界は `2**53-1` 以下を要求する。既存整数式の安全域 `2**60-1` も守り、
JSONをJavaScriptへ渡しても費用整数を丸めず比較できるよう、新しい費用だけに厳しい上限を置く。
互いに排他的な候補も上界では全部足すため保守的な拒否になり得る。
違反は `INTEGER_EXPRESSION_LIMIT` と費用項目のpointerで、モデル構築前に返す。
浮動小数への切替や巨大な目的重みで回避しない。

## 目的・基準・結果

不足合計人分、#66で定める不足評価、指定 `objectives` の順。
`scheduled_cost` を指定順で扱い、低費用のために不足や必須違反を増やさない。
`preference_penalty` や公平性を費用の重みへ換算しない。
上位の最適性未証明なら既存の探索停止規則を使い、費用最適とは主張しない。

`cost_summary` は対象外ならnull、対象なら `currency`、`units_per_currency`、
`evaluation_period`（W）、`total_units`、
`employees`（`employee_id`、`units_per_minute`、`scheduled_minutes`、`cost_units`）を返す。
勤務0の人も0で載せる。目的値は `total_units` と一致させる。
費用が最適でも不足最小性や他目的の証明を追加しない。
独立 `verify` は勤務区間と入力単価から集計し直し、最適性フラグはfalse。

#67との結合では、期間を越す勤務の費用はWへの投影分だけを評価する。
過去の確定支出・未来部分の費用をWの費用へ含めない。同じ単価で非重複期間に分割すれば合計は一致する。
これは計画内費用の最小化であり、期間外に押し出された費用や全契約期間の最小化ではない。
全期間の費用判断が必要なら評価するWを広げる。

`make_baseline` は旧入力のcostsを保持し、旧解を旧単価で再検証する。
再計画は新単価で計算する。単価だけ変更して勤務・担当を変えなければ `plan_changes=0`。
旧費用と新費用の差を勤務変更の効果と自動で説明しない。
新旧を比べる利用側は同じ通貨・倍率・対象期間・単価で別に再評価する。
基準計画のみに残る退職者に新単価を要求せず、新Requestの登録者について網羅する。

## 具体例と期待値

全例とも2026-10-07、Asia/Tokyo、粒度30分。
Alice/Bobとも有資格で09:00〜10:00の休憩なし候補、需要1人、必須制約なしとする。
費用表は上のJSON。必要以外の候補・需要はない。

| 条件 | 期待値 |
| --- | --- |
| 費用目的だけ | 両案とも勤務60分・不足0。Aliceは108000費用単位＝1800、Bobは144000＝2400。Aliceを選ぶ |
| Aliceの役割回避単価1、目的は費用→選好 | Alice、費用108000、選好60。Bobの選好0を費用より優先しない |
| 同じ条件で選好→費用 | Bob、選好0、費用144000 |
| Aliceは勤務不可、Bobの費用が高い | Bobで不足0。無勤務・費用0・不足60人分へ逃げない |
| 候補なし | 不足60人分のPARTIAL、勤務費用0。0を需要充足と誤読しない |
| 両者を固定勤務にする、需要は1人 | 待機を含め勤務120分、費用252000＝4200。過剰な役割配置はしない |
| Aliceの単価を同じ勤務のまま2000へ変更 | 変更量0、費用120000。過去の基準の108000は旧単価の値 |

90分候補に30分休憩があれば、担当0でも勤務60分・費用108000。
分割勤務09:00〜10:00と12:00〜13:00は勤務120分・費用216000で、間の120分には課金しない。
10月31日22:00〜11月1日06:00、02:00〜03:00休憩の勤務は全420分。
同じAlice単価で10月分216000、11月分540000、合計756000費用単位となる。

## 実装単位と受け入れ

| 実装順 | 必要な変更と検証 |
| --- | --- |
| Schema・意味検証 | 対応版、roster限定、対指定、集合一致、整数・上界。旧版は新フィールドを拒否 |
| 候補係数・目的 | 既存の勤務分数へ従業員単価を掛け、CP-SATの辞書式目的へ追加。全探索で不足・費用・選好の辞書式最小と一致 |
| 独立集計・Response | 元segmentsと休憩から再計算。単価・勤務・集計の改ざんと目的値不一致を検出 |
| 基準・結合 | `make_baseline` 往復、単価変更、固定・勤務日時希望・#70との目的順、#67で期間分割した合計一致 |

期間別単価を必要とする利用例が来たら、従業員ごとの重複なし区間料金表と全勤務区間の被覆を追加検討する。
段階料金・残業は勤務選択間の相互依存があるため、候補への定数付与では代替しない。
導入時は対象期間、実績の累積、閾値、段階別係数、丸めを確定し、#67と合わせて別契約で設計する。
