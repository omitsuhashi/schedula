# 開発・検証方針

## 開発の順序

アルゴリズムと入出力契約を先に固め、通常のプログラムから利用できる状態を作る。
LLM 入力はその後に追加する。以下は開発を整理するためのひな形で、
個々の課題・担当・依存関係・受け入れ条件は `omitsuhashi/schedula` の GitHub Issues に置く。

| 作業 | 完了条件 | 前提 |
| --- | --- | --- |
| 参照実装の評価とエンジン導入 | 依存・契約・ライセンスを確認し、担当配置と CP-SAT を同じ環境で実行検証。結果と環境を記録する | 本ドキュメントと ZIP |
| 共通契約の固定 | 空値、需要、履歴、候補、目的、状態をレビューし、schedula 用スキーマの配置・版・移行方針を決める | 参照実装の評価。契約と実装を並行して照合する |
| 業務条件の拡張 | 変更最小化、日付をまたぐ勤務、契約・暦の条件などを一つずつ定義し、結果検証まで対応する | 中核の実行検証と共通契約 |
| 利用者向け配布 | CLI・SDK・API の利用例、失敗時の扱い、運用上限、配布・公開条件が揃う | 中核の検証と契約固定。拡張全件の完了を必須にはしない |
| 入力アダプターとデモ | フォーム・CSV からの変換とブラウザーデモで、採用ルール・診断・評価値を確認できる | 共通契約と利用入口 |
| LLM 入力と説明 | RequestDraft の未解決項目を扱い、確認済み Request だけを実行し、結果の根拠だけで説明する | 中核と通常入力の検証 |
| 探索の改善 | 同じ条件・計算予算で標準方式と比較し、有効性・評価・時間の改善を示す | 再現可能な評価データと基準 |

拡張の優先順位は利用例を踏まえて Issue で決める。
研究方式の実装を、初期エンジン完成の条件にしない。

## Python 環境と依存管理

セットアップと依存管理の正本は [Python セットアップ](python-setup.md)とする。
パッケージ追加は `uv add`、環境同期は `uv sync`、実行は `uv run` に揃える。
Python 3.14.8 を固定し、jsonschema・OR-Tools と開発依存の Ruff・pytest・pre-commit を導入した。
`unittest` で書かれた既存テストは pytest から実行し、CI も同じ uv 環境と検証入口を使う。
独立した `assignment` は実行コードと検証を導入した。
現在の対応範囲は [利用手順](assignment.md)、実測は [担当配置の検証記録](evaluations/assignment.md)を参照する。
担当配置の CP-SAT と時間横断条件は Issue #7 で導入した。
実測は [時間横断配置の検証記録](evaluations/linked-assignment.md)に記録する。
勤務計画・候補展開・計画前履歴は Issue #8 で導入した。
利用手順は [勤務計画](roster.md)、実測は [勤務計画の検証記録](evaluations/roster.md)を参照する。
目的順序・共有探索予算・途中終了時の解保持は Issue #9 で導入した。
実測は [目的順序・終了状態の検証記録](evaluations/objectives.md)を参照する。
利用手順・スキップを検出する CI・wheel の隔離導入・架空入力の実行評価は Issue #10 で整備した。
入力作成から結果の判断までの入口は [README](../README.md)、
測定条件と結果は [利用入口・CI・実行評価](evaluations/runtime.md)を参照する。

## 参照資料の検証状態

ZIP の [TEST_REPORT.md](reference/skillshift-starter-0.1/TEST_REPORT.md)は、
Linux / Python 3.13.5、jsonschema 4.26.0、pytest 9.0.2、OR-Tools 未導入の環境で
`196 passed / 28 skipped` と報告している。
成功件数には150件の小規模担当配置を全探索と比較したテストを含む。
CP-SAT の28件は依存がなくスキップされており、構文確認だけで動作を検証したとは扱わない。

これは ZIP 作成時の報告である。2026-10-04 の文書整備ではエンジンのテストを再実行していない。
このリポジトリの CI やデプロイ入口のテスト結果にも置き換えない。
エンジン導入時に、実行環境・依存版・コマンド・成功・失敗・スキップと理由を改めて記録する。

2026-10-05 の [Issue #5 の評価](evaluations/engine-introduction.md)では、原本と ZIP の一致を確認し、
OR-Tools 導入下で参照テストと例を実行した。初回は222成功・1失敗・1スキップ、
未変更の再実行は223成功・1スキップだった。参照コードの取り込みは利用条件が未確定のため保留する。
実行用 Schema の配置・版・入口は [入出力契約](io-contract.md)で確定し、
出力の構造検証と探索予算の修正条件は評価記録から後続実装に引き継ぐ。

## 中核で確認すること

| 対象 | 必要な検証 |
| --- | --- |
| 入力の拒否 | 未知項目・ルール、不正参照、重複 ID / JSON キー、非有限数、曖昧な需要、未解決履歴 |
| 時間と候補 | 半開区間、粒度、計画端、ローカル日付、休憩、テンプレート展開、時計変更、候補上限 |
| 最小費用流 | 小規模問題の全探索との最適値・不可能性の一致、技能の取り合い、空需要、選好違反が必要なケース |
| CP-SAT | 依存導入下でスキップ対象を実行し、共通問題を最小費用流と比較。小規模勤務計画も全探索と照合 |
| 独立検証器 | 意図的に壊した解から、技能違反・二重配置・不足・過剰配置・休憩中の配置・各勤務ルール違反を検出 |
| 目的順序と状態 | 上位目的の未証明、段階間の時間切れ、実行可能解保持、依存不足、内部エラー、解を返す条件 |
| 出力契約 | Response Schema、診断の参照・数値、目的値の再計算、`status` と検証結果の整合 |

ZIP 作成時の `223 passed / 1 skipped` は期待件数だったが、上記の再実行で実測値を得た。
件数だけを目標にせず、CP-SAT の対象経路が実際に実行され、
依存未導入専用テスト以外が理由なくスキップされていないことを確認する。

参照コードを展開した隔離環境での確認例は次のとおり。
現在の schedula には参照の Python パッケージを導入していないため、
リポジトリ直下の実行手順として使わない。ZIP を展開した `skillshift-starter/` の
`pyproject.toml` があるディレクトリで実行する。元パッケージの `dev` は
`dependency-groups.dev` ではなく extra なので、`cp-sat` とともに明示する。
同期後の実行にも同じ extras を指定する。

```sh
uv sync --extra dev --extra cp-sat
uv run --extra dev --extra cp-sat pytest -q
uv run --extra dev --extra cp-sat python -m skillshift solve examples/assignment.json
uv run --extra dev --extra cp-sat python -m skillshift solve examples/linked_assignment.json
uv run --extra dev --extra cp-sat python -m skillshift solve examples/roster.json
```

## 実務規模の評価

人数、役割数、技能の偏り、計画日数、時間粒度、候補数、必須ルールと目的順序を記録する。
同じ入力・候補・時間予算で、必須条件違反、解が得られる割合、目的値、
最適性の証明、各処理の時間、メモリを比較する。
`scripts/evaluate.py` は保存済みの入力ごとに新しいプロセスで `solve` 全体の所要時間と
プロセスのピーク RSS を測る。探索予算、目的の証明範囲、検証結果は測定値とともに保存する。
30人・7日の担当配置と20人・7日・560候補の勤務計画は、実務規模未確定のため提案値である。
小規模の全探索一致を、そのまま大規模性能や全業務での正しさの証明にしない。
測定結果から公開時の入力上限・応答期限を決める。現時点で応答時間の目標値は未設定。

## 評価結果と実行ログの保存

採用判断や改善比較を後から検証できる記録を Git に残す。通常の再実行は記録を増やす目的でコミットしない。

| 保存先 | 残す内容 |
| --- | --- |
| `docs/evaluations/inputs/` | 再現用の架空入力と、評価文書に記載する生成条件 |
| `docs/evaluations/*.md` | 評価の目的、合格基準、実行コマンド、入力・source・環境・依存版、集計、採否理由と未確認範囲 |
| `docs/evaluations/results/` | 上記の判断で参照する測定の生データ。失敗・時間切れ・未実行も含む全試行、母数、目的値・証明範囲、時間・RSS・SHA を保持する |
| Actions の実行ログ・`pytest-results` artifact | 通常の CI のテストログと JUnit XML。成功・失敗・スキップ理由を追跡し、実行 URL と要点を PR / Issue に記録する |
| Git 対象外の `test-results/` | 手元のテスト結果と通常の再測定出力。採用判断に使う場合だけ、入力・条件・集計とともに評価記録へ追加する |

通常の測定では `--output test-results/evaluation.json` を使う。
比較に採用する測定は実行日と用途を名前に付け、評価文書から生データへリンクする。
既存の採用記録は上書きせず、再測定を別の記録として残す。成功した試行だけを抜き出さない。
全テストログや毎回の全出力・全解を Git に蓄積せず、診断の条件変更案など独立再検証に必要な入力・解は生データに含める。
今回の [性能評価](evaluations/performance.md) と [採用した探索予算・改善結果](evaluations/search-budget.md) は、比較と失敗の追跡に使った生データを保持する。

## 公開の条件

初回のライブラリ・CLI 公開には、採用機能の実行検証、入出力版と変更方針、
再現できる入力例、対応範囲・状態の説明、ライセンス、依存ライセンス表示、
セキュリティ窓口を揃える。データや研究コードを配布に含める場合は、それぞれの利用条件を確認する。

API 公開には加えて、認証・データ保持、入力上限、隔離、キャンセル、応答期限、
障害診断を設計・検証する。実在の従業員情報をログや公開デモへ流す仕様は別途決める。
デモ・評価データは架空または公開可能なデータを使う。
休憩や勤務間隔の試験値を法令・就業規則の推奨値として示さない。

実際のデプロイは [README](../README.md) にある環境と同一成果物の運用へ接続する。
現在の `scripts/deploy` はデプロイ先未実装の入口であり、Web API 公開機能とは区別する。
production の承認者・保護、ビルド、デプロイ先を決めてから release workflow を導入する。

| 未決定事項 | 決める内容 |

| 契約の安定化と配布 | 配置・`$id`・変更方針と実行用 Schema は実装済み。安定版、旧版の対応期間、SDK 生成の導入は未決定 |
| 勤務の拡張 | 契約0.2の夜勤・分割・日付/履歴境界は採用済み。店舗間移動や追加の候補生成方式は未決定 |
| 評価の拡張 | 明示目標分数との公平性・時間枠状態の変更最小化は採用済み。契約比率・費用・需要の上下限の別表現は未決定 |
| 診断 | 十分集合と許可編集の検証済み案は契約0.2に採用済み。最小矛盾集合・最小変更保証・提案のUIは未決定 |
