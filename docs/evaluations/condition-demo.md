## 実計算と公開の独立検証で確定した性質

| 教材 | 初期 | 条件だけの変更と結果 |
| --- | --- | --- |
| 担当時間上限 | Aの上限120分、合計担当180分、不足0人分 | 上限90分で担当150分・不足30人分、0分で担当60分・不足120人分 |
| 勤務時間上限 | Aの上限240分、合計勤務300分・担当240分。待機60分を勤務量に含む | 上限180分でAの240分候補を採用できず、勤務60分・不足180人分。300分では初期と同じ量 |
| 期間別勤務量 | 週10月5〜12日、Aの下限0分・上限360分、合計勤務180分、不足0人分 | 下限180分でAの2勤務を選び充足。270分では候補の最大180分を満たせず `INFEASIBLE`。上限0分で2日目に60人分不足 |
| 月の勤務量 | 上記と同じ計画期間10月5〜7日、文脈は10月1日〜11月1日 | 評価期間だけを月へ変更するとAの確認済み実績300分を含む。90分の候補は上限360分を超え、Aを採用せず不足60人分 |

初期・変更・復元の18段階を実solveで検査した。解のある17段階は元Requestと公開verifyで検査した。
`INFEASIBLE` は解なしのためverifyを適用できず、不足0や有効な計画として扱わない。下限390分・上限360分の逆転は別途 `INVALID_INPUT` と確認した。
公開verifyは有効性・不足を確認するが、不足最小性と目的の最適性を付与しない。
個人名・同率解の配列順・全勤務表を固定せず、需要保持・上限下限・分数・候補間休息の性質を確認する。

## 表示と回帰

変更した条件とAの実際の分数を初期→現在のカードで比較し、不足合計と不足する時間帯を先に表示する。
適用条件の表で評価期間・下限・上限・実際の分数を並べる。休息の表は前勤務終了・次勤務開始・間隔・必要量・採用の可否を示す。
解なしの場合は入力差分を開き、入力と状態を比較する。人数不足以外の必須条件を緩めない。

`tests/test_condition_demo_lessons.py` は公開verifyと別の分数計算で条件の充足を確認する。
`tests/condition-browser.cjs` は一覧・直接リンク・主要フォーム・ガイド・未計算・比較・復元、下限上限の逆転、週／月変更を実Chromiumで確認する。
1440px／390px、表へのキーボードフォーカス、強制配色、UTCのブラウザーでの日付・Asia/Tokyo表記も確認した。
従来の12教材とJSON・複合フォーム・100人30日・入力確認・保存記録のブラウザー回帰は成功した。

## 実測条件と限界

Python 3.14.8、OR-Tools 9.15.6755、Playwright 1.62.1、Chromium 151.0.7922.34、1 worker、seed 0、探索予算5秒。
冷起動は新しいPythonプロセスのimport・solve・有効な解のverify・終了までを含み、OSキャッシュは消さない。
継続は同一プロセスで各段階3回。最初の計測にはプロセス内の初回依存読込を含む。
HTTPはPOSTの往復・応答受理・DOM更新・2回の描画待ちまでで、ページ／教材GETは含まない。全体回帰も同じホストで稼働していた。
18段階の冷起動18標本・継続54標本、HTTPから描画まで20標本を保存した。
最大は冷起動0.5375秒、継続0.3571秒、HTTPから描画まで48.1ms。継続の初回は暫定目安0.25秒を超えたため、目安を全標本で達成したとは扱わない。
初回の依存読込後の53標本は最大0.0110秒だった。初回と後続を混ぜず、少数標本から一般的な性能を保証しない。探索予算と総応答時間は区別する。
環境、入力・画面・テストのSHA-256、全段階の実測と検証を[生記録](https://github.com/omitsuhashi/schedula/blob/3531385509b6cd25900a09f620127c36c2ada14f/docs/evaluations/results/condition-demo-20261010.json) に保存する。
