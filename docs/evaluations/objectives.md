2026-10-06、Issue #9 の実装を schedula 0.1.3 で検証した。
macOS 26.7.1 ARM64 / CPython 3.14.8 / uv 0.12.23、jsonschema 4.26.0、
OR-Tools 9.15.6755、pytest 9.1.1、Ruff 0.16.10、pre-commit 4.6.2 を使用した。
参照コード・Schema・JSON の原本は変更していない。入出力契約版は0.1を維持する。

## 実装と観測結果

CP-SAT は `objectives` の順に同じモデルを解き、証明済みの上位目的値だけを固定する。
上位目的が `FEASIBLE` なら後段へ進めない。後段の `UNKNOWN` や段階間の予算切れでは、
直前の解と証明済みの先頭部分を保持する。返す解の全目的値を独立に再計算し、
解・目的値・証明範囲・Response の検証に成功した場合だけ正式な解を返す。
後段の `INFEASIBLE`、モデル不正、内部例外では `INTERNAL_ERROR` として解を返さない。

探索予算は依存読み込み・候補展開・初期モデル構築の後から全段階で共有する。
`SEARCH_STATS` 診断の `facts` に予算と探索開始後の所要時間を記録し、
`stats.elapsed_seconds` は入力・結果・Response の検証を含む呼び出し全体を測る。
段階間の値取得・固定・目的更新も共有予算に含む。外部応答期限を保証する値ではない。

Ruff は正本の hook を使わない場合の同等コマンドで実行した。
初回の参照例のテストでは担当切替の期待値を4として1件失敗した。
休憩・待機を挟む担当変更を数えない定義と独立検証に従い、期待値を0に修正した。
最終の全件実行に未解決の失敗はない。GitHub CI の結果は PR に記録する。

勤務計画の CLI の単発観測は、共有探索予算10秒、探索開始後約0.071秒、
依存読み込みを含む総時間約0.347秒だった。実務規模の性能保証ではない。

## 全探索・状態・障害の検証

- 2人・2役割の勤務計画で目的順序の全6通りを元 JSON の独立全探索と比較した。
  選好優先ならペナルティ0・勤務90分・切替1回、勤務量優先なら60分・ペナルティ30・切替1回、
  切替優先なら0回・ペナルティ0・勤務150分となり、期待する優先順位で異なる解を選んだ。
- 担当配置の2目的も両順序を全探索と照合した。時間横断配置80件と勤務計画60件の既存全探索を
  空目的・単一目的・複数目的の順序付き評価値へ拡張し、実行可能性と辞書式最適値を比較した。
- 元の `roster.json` を目的を削らずに実 CP-SAT で解き、60・2640・0の全目的証明済み解を得た。
- 実際に求めた変数値を使い、各段階で `FEASIBLE` を注入してその段階で停止することを確認した。
  証明範囲は先頭から `false/false/false`、`true/false/false`、`true/true/false` となる。
- 解なしの `UNKNOWN`、後段の `UNKNOWN`、1段目・2段目終了直後の予算切れを制御して確認した。
  解なしは未検証・`solution: null`、解ありは直前の解と証明範囲を保持した検証済み `FEASIBLE`。
  極端に短い実時間制限だけに依存せず、既存の実 CP-SAT の時間切れ統合試験も実行した。
- 制御時計では初期準備・読み込みに300秒、各探索に2秒、解検証・Response 検証に450秒を割り当て、
  各段階の予算10・8・6秒、探索所要6秒、総時間756秒を別々に確認した。
- 各目的の値の破損、証明範囲の逆転、全目的証明済みなのに `FEASIBLE`、結果の目的順の逆転を拒否した。
  時間切れで保持した解を壊した場合も独立検証で拒否した。
- 初段の `INFEASIBLE` と、解が残るはずの後段の `INFEASIBLE` を区別した。
  初段・後段の `MODEL_INVALID`、内部例外、段階間のモデル検証失敗は正式な解にしなかった。
