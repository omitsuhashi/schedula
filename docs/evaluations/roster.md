# 勤務計画の検証記録

検証日: 2026-10-06（Asia/Tokyo）。対象: [Issue #8](https://github.com/omitsuhashi/schedula/issues/8)。
前提の Issue #7 は完了済みで、main の `0125664` から実装した。
[参照実装の評価](engine-introduction.md)・[時間横断配置の検証](linked-assignment.md)と区別して、
今回の schedula コードを実行した。保存済み原本8件のサイズ・SHA-256 は manifest と一致する。

## 実装と契約

勤務候補の選択と担当配置を同じ CP-SAT モデルで決める `roster` を導入した。
明示候補、休憩、待機、1人1日最大1勤務、勤務量上限、勤務間の休息、連勤、計画前履歴を扱う。
担当時間・担当切替の既存制約も適用し、独立検証器がすべての条件と単一目的を照合する。
テンプレートは決定的に展開し、明示候補と合成する。除外前の直積数も含めて5000件に制限する。
詳細は [勤務計画の利用手順](../roster.md)に記録した。

Request / Response Schema の構造・意味と契約版0.1を維持し、対応機能をパッケージ版0.1.2で記録する。
依存の追加・更新はなく、`uv.lock` の差分は schedula の版だけである。
保存済み参照コードは取り込まず、業務仕様からコード・テスト・利用例を実装した。
参照 `roster.json` はテストで入力データとして読み取り、メモリ上で目的を一つに制限して解いた。
原本の複数目的は引き続き拒否し、Issue #9 に残す。

## 全探索・境界・障害経路

- 2人・2日・2役割、各日最大3時間枠・合計8勤務候補の小規模入力60件を、元 JSON からの
  独立した全探索と照合した。候補の全部分集合と需要枠への担当者を列挙し、ソルバー・正規化表・
  検証器を呼ばず必須条件と評価値を計算した。実行可能13件・不可能47件で、実行可能性と最適値が一致した。
- 空目的、選好、勤務量、担当切替、休憩位置、担当時間・切替上限、勤務量・休息・連勤上限、
  計画前履歴を変えた。技能の組合せが必要な別の例で、人数だけでは担当できない場合も確認した。
- 参照例を1目的に制限した入力で、32候補・8勤務・ペナルティ60を確認した。
  新しい利用例も同じ業務条件を持つ。原本の複数目的の入力は明示的に拒否した。
- 担当30分・勤務量60分の違い、待機を含むこと、休憩を除くことを確認した。
  分数上限の未満・一致・余裕、従業員ごとの適用、同じ対象への複数ルールも試した。
- 勤務間と履歴からの休息1260分に対する上限1259・1260・1261分を確認した。
  連勤は履歴1日と計画内2日を加えた3日、休日によるリセット、履歴が上限を超えた場合の休日を確認した。
- 終業00:00の半開区間、隣接した勤務可能時間、複数休憩、休憩・待機を挟んだ担当切替を確認した。
  同日の分割勤務は選択できず、休憩中の担当や候補外の時刻への拡張もしなかった。
- 空履歴、古い最終勤務、直前日の最終勤務、計画開始と一致する最終勤務終了を受理した。
  履歴の欠落、最終勤務と連勤数の矛盾、計画内への重複、秒付き履歴は依存読み込み前に拒否した。
- 明示候補の計画期間外・勤務可能時間外と、テンプレートの除外を区別した。
  休憩部分だけが勤務可能時間から欠ける明示候補も拒否した。
- テンプレートの配列順序を変えて候補集合・IDの一致、明示候補との合成、
  休憩位置ごとの代替候補、ID衝突、展開前5000件の受理と5050件の拒否を確認した。
- `America/New_York` の時計変更で存在しない始業02:30と曖昧な始業01:30を拒否した。
  オフセット付きの明示候補では、時計変更をまたぐ実時間60分の勤務を解き、同じ評価値を再計算した。
- 壊した解の勤務欠落・候補不一致・重複勤務・同日の複数勤務・休憩中配置・勤務量・担当時間・
  休息・連勤違反を検出し、`INTERNAL_ERROR` / `solution: null` にした。
  ソルバー用の勤務候補・勤務可能時間・資格・需要・費用の表を空にしても違反を検出した。
- テンプレート由来の正常な解も、ソルバーの候補表を空にして検証した。
  目的値の不一致は `FEASIBLE` でも公開を遮断した。
- OR-Tools の依存不足を注入し、最小費用流へ退避しないことを確認した。
  実際の wheel の隔離実行でも OR-Tools が不在であることを確認し、`assignment` は `OPTIMAL`、
  時間横断配置・勤務計画は `BACKEND_UNAVAILABLE`、非対応の最小費用流は `INVALID_INPUT` だった。
- 実際の探索予算1nsで `UNKNOWN` を確認した。`FEASIBLE`・`INFEASIBLE`・`MODEL_INVALID` の
  状態変換はネイティブ境界への状態注入で確認し、`FEASIBLE` の変数値には実際に探索した解を使った。

CP-SAT の基本条件と状態の取り扱いは
[従業員スケジューリングの公式例](https://developers.google.com/optimization/scheduling/employee_scheduling)と
[CP-SAT の公式説明](https://developers.google.com/optimization/cp/cp_solver)を確認した。

## レビュー指摘の修正

`31ea68c` に対するレビューを受け、勤務間休息の候補ペアごとの排他制約を削除した。
候補の勤務開始から勤務終了＋必要休息までを整数の分で表す optional interval とし、
従業員ごとの `add_no_overlap()` でまとめる。粒度の倍数でない休息値、
計画前履歴、1人1日最大1勤務の意味は維持する。

1人・2日・各日09:00〜17:00・必要休息17時間、休憩位置が異なる5000候補で、
実際のモデルを構築して区間制約5000件・非重複制約1件・日別制約2件、計5003件を確認した。
旧方式の625万件の休息排他制約を生成しない。これはモデル件数の検証であり、
当該5000候補を求解した時間・メモリの評価ではない。

テンプレートのタイムゾーン変換で発生する `OverflowError` も
`INVALID_TEMPLATE_TIME` の入力診断へ変換した。
`0001-01-01 00:00 / Asia/Tokyo` と `9999-12-31 23:30 / America/New_York` を含む入力を
`solve()` へ渡し、`INVALID_INPUT` と該当テンプレートへの参照を確認した。

同じ環境で `uv run --locked --extra cp-sat pytest -q -ra` を実行し、
757件と既存 subtest 6件が成功、失敗・スキップ0件、7.78秒だった。
勤務計画の対象3ファイルは164件成功、2.49秒だった。
Ruff の lint・format、`bash -n scripts/deploy`、`git diff --check` も成功した。
