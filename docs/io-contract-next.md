# 入出力契約0.2

2026-10-06、利用者が [Issue #19](https://github.com/omitsuhashi/schedula/issues/19) の
推奨仕様を承認した。以下は契約0.2の採用仕様である。
契約 [0.1](io-contract.md) は継続し、[ADR-0003](adr/0003-extended-roster-contract.md) に判断を記録する。
実装・検証の結果は各 Issue と PR #26 を参照する。

## 採用した業務上の判断

| 判断 | 採用を提案する意味 | 別の選択肢と影響 |
| --- | --- | --- |
| 勤務日・分割・期間境界 | 最初の勤務区間の開始日を勤務日とし、連勤も開始日で数える。1人1勤務日1候補を維持し、1候補は1〜4区間。区間間は非勤務で、勤務間の休息とは区別する。全区間が計画内の候補だけを扱う | 触れた全日を勤務日とすると夜勤明けも連勤に含む。複数区間を別勤務とすると区間間にも休息が必要になる。期間端で切る方式は勤務量・休息・固定部分の前後情報を追加する必要がある |
| 公平性 | 計画期間内の指定対象者だけを評価し、明示的な目標分数との絶対偏差を合計する。正規化と過去分の加算はしない | 契約時間に対する比率では目標0の意味と整数倍率を追加で決める必要がある。過去分を含める方式では評価期間別の実績入力が必要になる |
| 再計画・診断 | 勤務状態と担当状態の時間枠ごとの差を各1単位とする。固定は必須条件。診断は不可能性を証明した十分集合を返し、許可された具体的な変更案だけを別入力で再計算する | 勤務1件を1変更とすると短い変更と終日の変更を同評価にする。最小矛盾集合・最小変更案の保証には追加探索と別の計算予算が必要になる |

この3点は利用者の承認済みであり、#21〜#25 の実装・検証の条件とする。
休息や分割間隔の試験値は、実際の就業規則の値を決めるものではない。

## 勤務候補・勤務日・時間

0.2の明示候補は `id`、`employee_id`、`segments` を必須とする。
`segments` は1〜4件で、各要素は `interval` と `breaks` を持つ。
従来の候補直下の `interval` / `breaks` は0.2では受け取らない。

```json
{
  "id": "alice_split",
  "employee_id": "alice",
  "segments": [
    {"interval": {"start": "2026-10-06T09:00:00+09:00", "end": "2026-10-06T12:00:00+09:00"}, "breaks": []},
    {"interval": {"start": "2026-10-06T17:00:00+09:00", "end": "2026-10-06T21:00:00+09:00"}, "breaks": []}
  ]
}
```

- 区間は時刻順の正の半開区間とし、隣接区間を含め `前区間.end < 次区間.start` を必須とする。隣接した区間は入力者が一つにまとめる。重複・逆順・空区間を丸めたり結合したりしない。
- 休憩は各区間の厳密な内側にあり、互いに重ならない。1区間最大10休憩。区間間の非勤務を休憩として扱わない。
- 最初の区間の開始を `planning_window.timezone` で表した日付が勤務日。一つの候補が翌日へ続いても勤務日は一つ。1人・勤務日につき最大1候補を選ぶ。
- 選んだ勤務の最初の開始から最後の終了までを勤務の外側の区間とする。同一従業員の別勤務はこの外側の区間が重ならない。別の勤務を分割の間へ挿入することは認めない。
- 担当可能時間は各区間からその休憩を除いた集合。区間間・休憩中に担当を置かない。担当しない勤務時間は待機。
- 勤務量は全区間の実経過分数から休憩の実経過分数を引いた総和。待機を含む。外側の区間の長さや賃金時間とは区別する。
- `min_rest_minutes` は前の勤務の最後の終了から、次の勤務の最初の開始までに適用する。分割の区間間には適用しない。
- 新しい必須ルール `min_split_gap_minutes` は `id`、`type`、`employee_ids`、`limit_minutes` を持ち、同一候補の隣接区間間の実経過分数が下限以上であることを求める。未指定なら構造条件である正の間隔だけを求める。

日時の比較・分数・時間枠は UTC の実時刻を基準に計算し、日付の帰属だけ指定タイムゾーンを使う。
計画期間の両端はローカル00:00、粒度は計画開始からの実経過分数で揃える。
秒・端数分・粒度のずれは引き続き拒否する。オフセットが異なっても同じ実時刻を同一視する。
時計変更日にローカル日の長さを24時間と仮定しない。日跨ぎ休憩も実経過で扱う。

### テンプレート

0.2のテンプレートは `id`、`employee_ids`、`dates`、`start_times`、`segment_options` を必須とする。
`segment_options` の各要素が一つの候補形状で、その中に1〜4件の区間を置く。
区間は最初の出勤からの `offset_minutes`、`duration_minutes` と、区間開始からの
`offset_minutes` / `duration_minutes` を持つ `breaks` で指定する。
最初の区間のオフセットは0。後続区間は前区間より後に開始する。
`dates` / `start_times` は最初の区間のローカル開始、オフセット・長さは実経過分数である。

```json
{
  "id": "split_template", "employee_ids": ["alice"], "dates": ["2026-10-06"], "start_times": ["09:00"],
  "segment_options": [[
    {"offset_minutes": 0, "duration_minutes": 180, "breaks": []},
    {"offset_minutes": 480, "duration_minutes": 240, "breaks": []}
  ]]
}
```

曖昧なローカル開始・存在しない開始は拒否し、オフセット付きの明示候補を使う。
同じ入力から同じ区間と候補IDを生成する。ID の生成には契約版とテンプレートID・対象者・
開始時刻・全区間と休憩を含める。明示候補とのID衝突は拒否する。
期間外・勤務可能時間外のテンプレート由来の候補は除外し、明示候補は入力エラーとする。
勤務候補の件数上限は全サポート版で撤廃した。明示・生成候補は件数による拒否や切り捨てを行わない。

## 期間境界・履歴・連勤

明示候補の全区間・休憩は計画内に収まり、各区間全体が勤務可能時間に収まる必要がある。
期間端での切り捨てはしない。計画開始前に出勤して開始後に終わる夜勤、
計画終了後まで続く候補を扱うには、入力者が計画期間を広げる。
計画期間内の需要も同時に用意し、未指定時間の需要は引き続き0とする。

0.2の `roster` は全従業員について以下の履歴を必須とする。

```json
{
  "history": {
    "last_shift_end": "2026-10-06T00:00:00+09:00",
    "last_work_day": "2026-10-05",
    "consecutive_work_days_before_window": 2
  }
}
```

`last_work_day` は最終勤務の開始日の帰属であり、終了から推定しない。
最終終了は計画開始以下、最終勤務日は計画開始日より前で、最終終了の直前が属する日以前とする。
直前日が勤務日なら連勤数は1以上、直前日が休日なら0。連勤数の上限366を維持する。
三項目の欠落、片方だけが `null`、負の連勤数、日付の表現範囲より前へ遡る連勤数は拒否する。
空履歴は `last_shift_end: null`、`last_work_day: null`、連勤数0の組で明示し、不明を補完しない。
最後の夜勤が計画開始を超えて続く履歴は拒否する。

`max_consecutive_days` は勤務開始日がある日を1、ない日を0として暦日を進め、
直前日までの連勤を引き継ぐ。10月5日22:00〜6日06:00は10月5日の1勤務日である。
10月6日に新しい勤務を開始しなければ、6日で連勤は途切れる。
計画後の勤務との休息はこの入力の保証範囲外であり、固定された翌勤務も照合する場合は計画期間を広げる。
次期間へは最終勤務終了・最終勤務日と、次期間の直前日までの連勤数を明示的に引き継ぐ。

## 公平性

`fairness` は `evaluation_period` と `employee_targets` を持つ。
期間は計画期間と同じ実時刻の区間、対象は重複のない1〜250人で、
各要素は登録済み `employee_id` と0〜10,000,000の整数 `target_minutes` を持つ。
公平性目的 `fairness_deviation_minutes` と対にして指定し、片方だけなら `INVALID_INPUT`。

```json
{
  "fairness": {
    "evaluation_period": {"start": "2026-10-06T00:00:00+09:00", "end": "2026-10-07T00:00:00+09:00"},
    "employee_targets": [{"employee_id": "alice", "target_minutes": 240}, {"employee_id": "bob", "target_minutes": 480}]
  },
  "objectives": [{"id": "fairness", "metric": "fairness_deviation_minutes"}]
}
```

評価値は `sum(abs(scheduled_minutes[employee] - target_minutes[employee]))`。
単位は分で正規化しない。対象外の従業員を平均や偏差に含めず、目標を推測しない。
目標0は勤務量0に近づける選好であり、勤務禁止ではない。
目標の粒度一致は求めず、達成不能な目標も受け入れて偏差を返す。
技能・勤務可能時間・需要・勤務ルールが優先し、目標のために必須条件を変更しない。
契約時間を入力値の根拠にできるが、契約上の最低・最高時間をこの目的だけで強制しない。
過去実績を足す期間別の公平性、契約比率、給与額は本契約に含めない。

Response の `fairness_summary` は対象外なら `null`、対象なら期間・尺度 `absolute_minutes`・
`normalized: false` と、各人の `employee_id`、`target_minutes`、`scheduled_minutes`、
`deviation_minutes` を返す。同じ返却解から独立に再計算する。正式な解がなければ `null` とする。

## 比較元・固定・変更最小化

`baseline` は照合用の `plan_id`、旧 `source_request`、旧 `source_solution` を持つ。
旧入力は0.1または0.2の完結した roster 入力とし、`baseline` と `diagnosis` を含めない。
旧入力と旧解を旧契約で検証し、不正な構造・不明参照・勤務や需要の違反を含む基準は
`INVALID_INPUT` とする。旧入力では有効で新入力の欠勤・需要等に合わない旧解は受け入れる。
同じ計画期間の実時刻・タイムゾーン・粒度を要求し、時間軸を無言で変換しない。
`plan_id` は入力者の照合IDであり、承認・認証・実績の証明ではない。

新しい目的 `plan_changes` は比較元を必須とする。
各従業員・時間枠について、勤務状態を `off` / `work` / `break`、
担当状態を未担当または役割IDとして比較し、それぞれ異なれば1単位を加える。
分割間の非勤務は `off`、待機は `work` かつ未担当。
勤務状態と担当状態が両方変われば2単位。候補ID・入力順序・表示名だけの変更は0。
同じ実時刻の状態ならオフセット表記が違っても0。
単位は時間枠の状態成分数で、分数・勤務件数・人数に換算しない。

比較対象は旧入力と新入力の従業員IDの和集合とする。
削除された人の旧勤務・担当は削除分、追加された人の勤務・担当は追加分として数える。
人のIDの付け替えは別人の削除・追加。候補・役割の追加削除も同じ状態比較で数える。
候補の削除は基準を不正にしない。旧条件での資格・勤務可能時間を新条件で検証し直さない。
この尺度は変わった勤務件数や変更の心理的負担を直接評価しない。

`fixed_parts` は0〜1000件で、`id`、`employee_id`、`interval`、`components` を持つ。
固定を指定する場合も `baseline` を必須とする。
`components` は `work` / `role` の空でない重複なし配列で、該当時間の基準状態を必須条件として固定する。
固定していない時間・成分だけが変更可能。固定された非勤務・未担当も保持する。
固定対象は旧入力に存在し、区間は新旧共通の時間枠に揃える。
不明な固定参照は `INVALID_INPUT`、有効な固定状態と欠勤・需要等の矛盾は `INFEASIBLE`。
削除された従業員の有効な旧勤務を固定しても勝手に解除せず、実行不可能として扱う。
基準の候補IDが消えても、別の候補で同じ固定状態を再現できれば許可する。
同じ状態を再現する現候補がなければ `INFEASIBLE` とし、基準の候補を勝手に復活させない。
固定は目的より優先し、`plan_changes` が目的になくても適用する。

Response の `change_summary` は比較元なしなら `null`、ある場合は `plan_id`、
`unit: "slot_components"`、`work_changes`、`role_changes`、その合計 `total_changes` を返す。
固定状態とこの合計は、ソルバー変数ではなく新旧の共通解から独立に検証する。正式な解がなければ `null` とする。

## 目的・上限・途中終了

既存3目的に `fairness_deviation_minutes` / `plan_changes` を追加し、目的数の上限は5。
同じ指標の重複を拒否し、すべて整数の最小化として配列順を辞書式に優先する。
巨大な重みへの置換はしない。既存の共有探索予算と、証明済みの連続した目的範囲だけを
`proven_optimal: true` にする規則を維持する。途中終了時も同じ返却解の全目的値を再計算する。

時間枠3000、従業員250、役割50、従業員×時間枠×役割1,000,000の上限を維持する。勤務候補の件数上限は撤廃した。
固定・比較の従業員和集合は最大500人。`min_split_gap_minutes.limit_minutes` は既存の分数上限と同じ0〜10,000,000。
新しい入力も暗黙の丸め・小数係数を認めない。各目的・制約式の係数、変数範囲と保守的な総和上界を
モデル作成前に計算し、絶対値が `2**60 - 1` を超える入力は `INVALID_INPUT` とする。
上限は性能保証を意味しない。勤務候補の選択と担当配置を同じ有限モデルで決める。

## 不可能性診断と変更案

元の `INFEASIBLE` / `UNKNOWN` と `solution: null` は維持し、変更後の解で置き換えない。
既存の `diagnostics` と最小費用流の不足診断を保持する。
`diagnosis` を指定しない入力で追加の変更案探索は行わない。
`diagnosis` は0超〜300秒の `time_limit_seconds`、0〜10の `max_suggestions`、
最大100件の `allowed_changes` を持つ。通常の探索予算と独立に計測する。

`allowed_changes` の各要素は一つの明示的な選択肢で、`id` と最大10件の `edits` を持つ。
各編集は `json_pointer` と整数の `value`。対象は需要の `required_people` と、
対応済み必須ルールの `limit_minutes` / `limit_days` / `limit_count` に限定する。
ポインターは元入力の存在する項目を指し、同じ選択肢の同一項目への重複編集を拒否する。
値は対象の契約上限内とする。それ以外の編集先は未対応として入力エラーにする。
技能・従業員・勤務可能時間・候補・固定部分を作ったり変えたりしない。
異なる選択肢を勝手に組み合わせず、入力者がまとめた一つの選択肢の編集だけを同時適用する。

Response の `diagnosis_result` は次の意味を持つ。

| 内容 | 意味 |
| --- | --- |
| `status` | `COMPLETE` / `TIME_LIMIT` / `ERROR` / `UNSUPPORTED` / `NOT_APPLICABLE`。未要求なら結果自体が `null` |
| `conflict` | 不可能性を証明した条件の十分集合、または `null`。各条件は `code`、入力の `json_pointer`、`related_ids`、該当 `interval`（時間を持たなければ `null`）を持つ |
| 証明範囲 | `infeasibility_proven: true`、`minimality: "not_proven"`。集合と変更しない基本条件を合わせると解がないという範囲。唯一の原因・最小原因とは説明しない |
| `suggestions` | 各要素に `option_id`、具体的な `modified_request`、変更後の `response` を持つ。変更後の通常探索と独立検証に成功した `OPTIMAL` / `FEASIBLE` だけを掲載する |
| `suggestion_minimality` | `not_proven`。許可した選択肢の全探索や未許可変更との比較を保証しない |
| 計算記録 | `time_limit_seconds` と `elapsed_seconds`。予算内に完了しなければ完了済みの証明・検証済み案だけを保持する |

需要、役割の技能条件、従業員の技能・勤務可能時間、候補集合、勤務ルール、固定部分を入力へ追跡する。
抽出方式に対する未対応の条件も明示し、空の集合を「原因なし」と説明しない。
最初の実装では全必須条件の集合を十分集合として返してもよいが、参照と証明範囲を省略しない。
CP-SAT の不可能性証明を使える場合は追加の最小化探索を必須にしない。

元入力が `UNKNOWN` なら不可能性を証明した集合を返さず、`conflict: null` とする。
元入力が正常または `UNKNOWN` なら `NOT_APPLICABLE` とし、変更案探索を行わない。
このとき `suggestions: []` とし、理由はそれぞれ `ORIGINAL_FEASIBLE` / `ORIGINAL_UNKNOWN` とする。
診断の追加処理の失敗は `ERROR` で記録し、
元入力について既に得た `INFEASIBLE` を改変しない。
変更後入力は元入力の複製に許可編集だけを適用し、診断を無効にして再帰的な提案生成を止める。
変更後の状態・目的値・検証結果は変更後入力についての主張であり、元条件の正式な解ではない。
変更案が不可能・未確定・入力不正・検証失敗なら掲載せず、対象の選択肢と理由を診断に記録する。
追加予算は抽出・変更後の入力検証・探索・独立検証を含む。各処理開始前に残りを確認し、
変更後の探索予算を残り以下にする。元条件との違いは許可編集だけとし、
`solver.time_limit_seconds` の短縮と `diagnosis` の無効化は追加計算の設定として別に記録する。
実際の設定を `modified_request` に反映し、元の予算と適用予算を変更案の診断に残す。
これは処理の強制終了を行う外部応答期限とは区別する。
追加予算内に何の結果も取得できなければ `TIME_LIMIT`、`conflict: null`、`suggestions: []` を返す。
空の案を「許可範囲にも実行可能な変更はない」という証明にしない。

## 0.1からの移行

入力者が版を0.2に変え、各候補の `interval` / `breaks` を一つの `segments` 要素へ移す。
旧テンプレートは勤務長と休憩位置の直積ごとに、一つの区間を持つ `segment_options` 要素へ変換する。
旧履歴の `last_work_day` は入力者が確認して追加する。0.1で有効な日勤履歴でも、
変換処理が終了時刻から勤務日を補完したとは扱わない。
需要・資格・既存ルール・目的順序は変更しない。新目的は利用者が選んだ順序で追加する。

```json
{
  "schema_version": "0.1",
  "shift_candidates": [{"id": "day", "employee_id": "alice", "interval": {"start": "2026-10-06T09:00:00+09:00", "end": "2026-10-06T17:00:00+09:00"}, "breaks": []}]
}
```

```json
{
  "schema_version": "0.2",
  "shift_candidates": [{"id": "day", "employee_id": "alice", "segments": [{"interval": {"start": "2026-10-06T09:00:00+09:00", "end": "2026-10-06T17:00:00+09:00"}, "breaks": []}]}]
}
```

上の JSON は移行箇所だけを示す。完全な Request ではない。
0.2の `solution.shifts` は `candidate_id`、`employee_id`、`work_day`、候補と同じ `segments` を返す。
旧 Response の勤務構造は0.1のまま保持し、旧解の比較時は状態比較用に明示的に読み分ける。

## 具体的な受け入れ例

以下はすべて架空の例。特記しなければ `Asia/Tokyo`、粒度30分、
勤務可能時間・担当資格は十分、需要は示した担当だけ、明示候補以外の候補なしとする。
正常例の `OPTIMAL` は小規模で探索を完了したときの期待であり、予算切れなら検証済み `FEASIBLE` を許す。

| 機能・種別 | 入力条件 | 期待する配置・評価・状態 |
| --- | --- | --- |
| 夜勤・正常 | 計画6日00:00〜8日00:00、Aliceが6日22:00〜7日06:00、休憩6日23:30〜7日00:30。休憩外に役割1人の需要 | 勤務日6日、勤務量420分。23:30〜00:30は担当なし、他はAlice。`scheduled_minutes = 420`、`OPTIMAL` |
| 夜勤・休息の境界 | 上の夜勤の次に7日14:00開始の必須勤務、休息下限480分 | 06:00〜14:00の480分で両方選べる。次勤務を13:30開始にすると450分のため `INFEASIBLE` |
| 夜勤・重複 | 6日22:00〜7日06:00と7日05:30開始の別候補を需要で両方要求 | 勤務日が別でも外側の区間が重なるため `INFEASIBLE`。壊した解は重複違反 |
| 夜勤・連勤 | 計画前の5日まで連勤2日、6日開始の夜勤を需要で要求、連勤上限2 | 6日で3連勤となり `INFEASIBLE`。上限3なら正常。7日に新しい勤務がなければ7日で0に戻る |
| 夜勤・期間外拒否 | 計画6日00:00開始に5日22:00〜6日06:00の明示候補、または履歴の最終終了6日06:00 | 切らずに `INVALID_INPUT`。計画を5日00:00へ広げ、需要・履歴を揃えて再入力する |
| 夜勤・終端/年境界 | 12月31日22:00〜1月1日00:00、計画終端1月1日00:00 | 半開区間として期間内。勤務日12月31日、勤務量120分 |
| 時計変更・秋 | `America/New_York`、2026-11-01の `00:00-04:00`〜`04:00-05:00` | 実経過300分。休憩なしで `scheduled_minutes = 300`。ローカル時計の差240分にしない |
| 時計変更・拒否 | 同地域のテンプレートで2026-11-01 01:30、または2026-03-08 02:30開始 | 前者は曖昧、後者は存在しない開始として `INVALID_INPUT`。明示オフセットで一意の実時刻を表す |
| 分割・正常 | 6日09:00〜12:00と17:00〜21:00を一候補で指定。各区間に需要 | 勤務日6日、勤務量420分。12:00〜17:00は担当なし。勤務間休息下限660分でも同一候補の5時間の間には適用せず `OPTIMAL` |
| 分割・間隔/分割数 | 上の分割で `min_split_gap_minutes = 300` / 330、または5区間を指定 | 300なら正常、330なら需要を満たせず `INFEASIBLE`。5区間は契約上限超過で `INVALID_INPUT` |
| 分割・拒否 | 09:00〜12:00と11:30〜14:00、または09:00〜12:00と12:00〜14:00 | 重複または隣接の非正規形として `INVALID_INPUT`。入力者が一つの区間にまとめる |
| 分割・次勤務休息 | 分割勤務の最終終了21:00、翌07:30から次の必須勤務、休息660分 | 630分なので `INFEASIBLE`。翌08:00開始なら660分で正常 |
| 公平性・異なる目標 | Alice/Bobに240/480分の目標。各人に240分・480分の候補があり、需要合計720分 | Alice240・Bob480を選び偏差0。総勤務量720、`fairness_deviation_minutes = 0` |
| 公平性・同一目標/非対称 | 両者の目標240分、技能上Aliceだけが480分を担当でき、Bobは勤務不可 | Alice480・Bob0。偏差240+240=480。技能・勤務可能時間を広げず正常 |
| 公平性・目標0/対象外 | Alice目標0で60分の需要をAliceしか満たせない。Bobは評価対象外 | Alice60、偏差60。Bobの目標を補完しない。目標0を勤務禁止にしない |
| 公平性・未指定/粒度 | 対象者の `target_minutes` なし、または目標45分で候補30分/60分 | 未指定は `INVALID_INPUT`。45分は受理し、どちらも偏差15。最適値15で到達不能を入力不正にしない |
| 公平性・目的順序 | 需要なし、Alice目標60分、60分候補あり | 公平性→勤務量なら勤務60・値(0,60)。勤務量→公平性なら勤務0・値(0,60)。各配列の指標順で値を読む |
| 再計画・正常/ID変更 | 有効な旧計画と条件同一。旧候補IDだけを別IDへ変える | 意味が同じ勤務・担当を返せ、`plan_changes = 0` |
| 再計画・欠勤 | 旧Aliceの09:00〜10:00勤務・担当を、欠勤でBobへ移す。粒度30分 | 2枠×2人×勤務/担当2成分=8単位。`work_changes = 4`、`role_changes = 4`、`total_changes = 8` |
| 再計画・休憩変更 | 旧計画09:00〜11:00、休憩09:30〜10:00。新休憩10:00〜10:30。両方とも残りは同じ役割を担当 | 勤務状態が2枠、担当状態が2枠変わり4単位。候補IDの一致で変更0としない |
| 再計画・固定衝突 | 欠勤するAliceの旧09:00〜10:00勤務状態を固定 | 有効な旧計画は受け入れ、新条件との衝突で `INFEASIBLE`。不明な旧従業員参照・旧解の二重配置は `INVALID_INPUT` |
| 診断・正常 | 一つの役割の需要2人に有資格者1人。許可案は同じ需要の1人への変更のみ | 元は `INFEASIBLE` / `solution: null`。需要・資格・勤務可能時間/候補の十分集合と、別入力で検証した1人の変更後解を返す。最小性は未証明 |
| 診断・技能の取り合い | 2役割を同時に各1人要求し、両方の有資格者はAlice一人だけ | 各役割だけの人数不足と断定しない。複数需要と資格・二重配置禁止を参照する不可能集合 |
| 診断・拒否/予算境界 | 許可案に技能の追加を指定、または追加診断の予算が尽きる | 前者は未対応編集として `INVALID_INPUT`。後者は `TIME_LIMIT` と完了した証明/案だけを返し、未検証案を掲載しない |
| 診断・未確定 | 元の探索が `UNKNOWN` | 不可能性の集合を作らず `conflict: null`。不可能と説明しない |

### 組合せ例

計画6日00:00〜8日00:00、粒度30分。Aliceの旧勤務は6日20:00〜22:00と
7日02:00〜04:00の一候補、各区間に同じ役割の需要。勤務日6日、勤務量240分である。
新入力ではAliceは後半勤務不可、Bobは後半だけ勤務可能、前半のAlice勤務・担当を固定する。
新候補はAlice前半とBob後半で、目標は両者120分。

`plan_changes` → `fairness_deviation_minutes` → `scheduled_minutes` の順なら、
Alice前半120分・Bob後半120分を選び、目的値は `(16, 0, 240)`。
夜勤/分割の旧計画を受理し、固定を守り、勤務日をAlice6日・Bob7日として独立検証する。
旧後半のAlice勤務も固定すると `INFEASIBLE`。変更許可がなければ案は空配列とし、
固定を外す提案を生成しない。この例は新旧計画の有効性、固定、変更尺度、公平性、
日付境界と診断が一つの結果で一致するための受け入れ条件である。
