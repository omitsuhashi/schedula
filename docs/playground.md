# 配置プレイグラウンドの画面・サンプル仕様

Issue [#27](https://github.com/omitsuhashi/schedula/issues/27) の推奨方針として、
**条件を左、担当配置と比較を右に置く1画面**を採用する。
以下の固定条件・編集上限は担当配置フォームに適用する。JSON 入力の拡張は末尾に記載する。
初めて使う人が入力を準備せず、条件を一つ変えて結果との関係を確かめるためのデモである。
画面実装は #28〜#31 で導入した。本書・[画面案](playground-wireframe.html)・
[サンプル](../examples/playground/lunch.json)・[操作定義](../examples/playground/scenarios.json)を仕様の正本とする。
実際の利用手順は [README](../README.md#ブラウザーで担当配置を試す)、
実ブラウザー・実エンジンの確認は[デモの検証記録](evaluations/playground.md)を参照する。

## 採用する構成

| 判断 | 採用内容と理由 |
| --- | --- |
| 対象 | JSON 契約0.1の `assignment`。出退勤・休憩を決めず、担当資格・勤務可能時間・需要の関係に集中する |
| 画面 | HTML・CSS・JavaScript 各1ファイルを基本とし、標準の `table`、`input`、`select`、`button`、`details` と `fetch` を使う |
| 実行 | Python 標準の `ThreadingHTTPServer` / `BaseHTTPRequestHandler` で限定した静的ファイルと計算入口を配信し、既存 `solve` を呼ぶ |
| 依存 | 既存の jsonschema とエンジンを再利用。フロントエンドのビルド、UI フレームワーク、追加 Web 依存は導入しない |
| 最適化 | `backend: auto`、探索予算5秒、seed 0。追加制約・選好・目的は空配列とし、最小費用流で成立する配置を求める |
| 保存 | 入力・比較元・結果はその画面のメモリ内だけ。再読み込みで通常サンプルへ戻る |

単純な表で6人・6時間枠を読み比べられるため、ドラッグ操作の時間軸部品は不要と判断した。
上下だけに並べる案は入力と結果が離れ、手順ごとの別画面は自由編集と比較を往復しづらいため採用しない。
狭い画面では同じ DOM を条件→結果→比較の縦並びにする。

[ADR-0001](adr/0001-json-first-engine.md) の Request → Response と、
[設計方針](design-policy.md) の独立検証・必須条件の維持に従う。
API 公開、変更最小化のフォーム、認証は対象外とする。JSON 入力では既存エンジンの勤務計画も扱う。
`OPTIMAL` はこの入力での状態であり、目的が空の本サンプルで「最良の従業員を選んだ」と説明しない。

## 画面と操作の対応

[静的な画面案](playground-wireframe.html)は通常状態と欠勤時の説明をレビューするためのもの。
計算・条件編集は未実装であり、操作部品は無効にしている。掲載する配置は実測した一例で、受け入れ条件ではない。

| 領域 | 表示・操作 |
| --- | --- |
| 上部 | 「配置プレイグラウンド」、架空データの表示、2026-10-06・11:00〜14:00・30分粒度 |
| シナリオ | 「通常のランチ営業」「急な欠勤」「ピーク時の必要人数増加」を一つの選択欄で切り替える |
| ガイド | 次に変える欄・値・再計算後に見ること。「この変更を入力」は同じフォームを更新するだけで、計算は明示ボタンから行う |
| 左・従業員 | 名前、3技能のチェック欄、勤務可能時間の開始・終了、終日「勤務不可」 |
| 左・需要 | 役割を行、6時間枠を列とする必要人数の整数入力。0人も明示する |
| 操作 | 主ボタン「再計算」、副操作「サンプルへ復元」、ガイド内「自由に編集する」 |
| 右・結果 | 状態の文字、独立検証の有無、実行した条件。従業員×時間枠に役割名を記載し、別表に役割別の配置人数／必要人数を載せる |
| 右・比較 | 元の条件・実計算結果と現在の実計算結果。入力差分を先に示し、両方に有効な解がある場合だけ担当差分を表示する |
| 補助詳細 | 診断の `code`・入力箇所・`facts`、目的と証明範囲、総処理時間。JSON は折り畳み内に読み取り専用で表示できる |

初回表示は通常サンプルを読み、直ちに実計算して比較元を作る。
最初の成功前は「計算中」または失敗状態を示し、埋め込み配置を実計算結果として見せない。
シナリオ選択でも同じサンプルを複製して実計算し、その後に変更ガイドへ進む。
自由編集はガイドを隠すだけで、条件・結果・比較元を保持する。

担当表の未担当は「担当なし」と表示する。勤務可能時間の外は「勤務可能時間外」と区別し、
欠勤・退勤・休憩・待機を推定しない。需要は最低人数でなく厳密な人数である。
色に加え役割名と状態を必ず書き、表には `caption` と行列見出し、入力には対象と時間帯を含むラベルを付ける。
エラーは欄の近くと一覧に出し、送信時は最初の不正欄へフォーカスする。状態更新は `aria-live="polite"` を使う。
小さい画面の横スクロールは表の領域内に限定し、キーボードで到達できるようにする。

## 3シナリオの受け入れ例

すべて同じ通常サンプルから開始し、初期結果は `OPTIMAL` / 独立検証成功。
担当人数の合計は30分×22人枠（延べ担当時間660分）で、勤務量・給与・目的値には使わない。
すべての成立例で担当資格・勤務可能時間・二重配置禁止・需要の一致を独立検証する。
配列順・同率解の人選・担当差分の件数は固定しない。

| シナリオ | 変更する条件 | 再計算後に確認すること | 復帰・復元 |
| --- | --- | --- | --- |
| 通常のランチ営業 | 11:30〜12:00のホールを1→2人 | `OPTIMAL`、検証成功、同枠ホール2人。合計23人枠 | サンプルへ復元→再計算で22人枠 |
| 急な欠勤 | あおいの勤務可能時間を空配列にする | `INFEASIBLE`、解なし。12:00〜12:30の調理は必要2人・担当資格があり勤務可能な従業員1人。全体は5人必要に対し5人が勤務可能なので、人数総数だけでは成立しない | あおいを勤務不可のまま、12:00〜13:00の2枠の調理を2→1人へ明示変更すると `OPTIMAL`・検証成功・20人枠。サンプルへ復元で欠勤と需要変更の両方を戻す |
| ピーク時の必要人数増加 | 12:00〜13:00の2枠のホールを2→3人 | `OPTIMAL`、検証成功、同枠で調理2人・ホール3人・皿洗い1人を同時に満たす。合計24人枠 | サンプルへ復元→再計算で22人枠 |

欠勤時の説明根拠は `INSUFFICIENT_QUALIFIED_EMPLOYEES`、`related_ids: ["kitchen"]` と、
`facts` 配列の `slot: 2` / `required_people: 2` / `eligible_people: 1`。
`facts` は `{name, value}` の配列である。返却される最初の不足を説明し、全矛盾の列挙や最小追加人数とは言わない。
調理需要の削減は架空シナリオで利用者が選ぶ条件変更であり、エンジンの自動緩和・実務上の推奨ではない。

操作定義の各 `steps` は順に適用する。`changes` は `employees` / `demand` ごとの ID をキーにした
項目置換で、配列値は全置換する。`restore: true` は適用前にサンプル全体を複製し直す。
`expected` は受け入れテスト用であり、画面の結果を生成するデータには使わない。
ガイド文・シナリオ ID・期待値はエンジンの Request に追加しない。

## 編集範囲・値の上限

| 対象 | 初版の許容範囲 |
| --- | --- |
| 従業員 | 6人固定。追加・削除・ID変更なし。表示名は前後空白を除いて1〜20 Unicode code points、空白のみ不可 |
| 保有技能 | 固定3種類の有無を切替。保有時レベル1、未保有時は要素なし。重複不可 |
| 勤務可能時間 | 0または1区間。11:00〜14:00の30分刻み、開始＜終了。勤務不可は `availability: []` |
| 需要 | 固定3役割×6枠。各セル0〜6の整数。空欄・小数・負数・NaN は不可 |
| 固定値 | 日付・タイムゾーン・粒度、技能・役割の ID とラベル・必要技能、需要 ID と区間、solver 設定 |
| 必須配列 | `shift_candidates` / `constraints` / `preferences` / `objectives` は `[]`。任意拡張フィールドは受け入れない |

需要の合計が6を超える入力や技能不足は有効な問題として計算し、`INFEASIBLE` を体験できるようにする。
表示名の重複は許すが ID は不変とし、参照・比較は ID を使う。
自由編集は上の範囲内を意味する。新しい従業員・役割・期間を必要とするときに、その拡張だけを後続で定義する。

## 表示モデル・検証の境界

ブラウザーの編集値は Request の複製を基本とする。未入力の数値など入力途中の文字列はフォームに保持し、
「再計算」時に妥当な値だけを確定 Request に変換する。空欄を0に、未知 ID を既存 ID に補正しない。
開始・終了は固定日付と `+09:00` を付ける。端末のタイムゾーンで変換しない。
表示名は `label`、技能チェックは `skills`、勤務不可と時間欄は `availability`、人数欄は `required_people` に対応する。
勤務不可で送信する `availability: []` と、画面で最後に選択した開始・終了時刻は区別する。
ガイドで他の項目を変更しても選択時刻を保持し、勤務不可を解除したときに戻す。サンプルへの復元は時刻も初期値に戻す。
入力編集時は比較元・結果の有無にかかわらず共通の検証を行い、修正済みのカスタムエラーを解除する。

1. ブラウザーは標準の入力検証と欄間チェックで修正位置を示す。サーバー検証の代わりにはしない。
2. ローカル入口は JSON の厳密な読み取りに `schedula.contract.load_json` を使い、重複キー・非有限数を拒否する。
   固定値、全 ID 集合と件数、18需要、名称長、技能・時間・人数の範囲をサーバーでも検証する。
   契約上は正しくてもデモ範囲外の入力は `DEMO_INPUT_OUT_OF_RANGE` と対象 `json_pointer` で拒否する。
3. 範囲内の Request はそのまま `solve` に渡し、既存の Schema・参照・時間・担当資格の意味検証、独立結果検証を使う。
   表示しやすくするために条件を落とさない。Response の状態・解・診断・目的・検証結果を保持する。

結果は `{input: 確定Requestの複製, response: 実Response}` の組で保持する。
比較元も同じ組を使い、フォームの後続編集で過去入力や比較元を変更しない。
比較元はサンプル入力で独立検証に成功した配置を得た時点で確定する。初回の失敗・未確定結果は現在の状態として保持し、比較元にしない。
それまでは変更ガイドを無効にして元の条件の再計算を案内する。条件を編集済みならサンプルへ復元して初期計算へ戻せる。
`request_id` は実行ごとに `playground_<通番>` とし、応答の一致を確認する。
比較対象からこの実行識別子を除き、ID・時間枠・役割を使って条件と解を比較する。
連続区間の担当を30分枠へ展開してから照合し、配列の並び順で比較しない。
名前のみの編集は入力差分として示すが、担当差分を発生させない。

## 画面の状態と古い結果

| 状態・条件 | 表示と操作 |
| --- | --- |
| 未計算 | 入力を表示し「まだ計算していません」。担当表は空 |
| 計算中 | 「計算中」。二重送信を止め、編集・シナリオ切替・復元も一時無効にする |
| 入力不備 | 欄と診断を関連付け、修正後に再計算。入力不備と `INFEASIBLE` を区別する |
| `OPTIMAL` | 検証成功時だけ担当表を表示。「条件を満たす配置です」。目的・証明範囲は詳細欄に保持 |
| `FEASIBLE` | 検証成功時だけ担当表を表示。「条件を満たします。最適性は未証明です」。各目的の `proven_optimal` を表示 |
| `INFEASIBLE` | 「この条件を満たす配置はありません」。現在の担当表は出さず、診断と入力修正へ案内 |
| `UNKNOWN` | 「探索予算内に結果が確定しませんでした」。解なしとは言わず再計算へ案内 |
| `BACKEND_UNAVAILABLE` / `INTERNAL_ERROR` | 実行失敗として診断を表示し、配置は出さない |
| 通信失敗・不正な応答 | エンジン状態を推測せず「結果を取得できませんでした」。再試行は利用者の操作から行う |
| 結果後に編集 | 「条件を変更しました。再計算が必要です」。前回結果は実行時入力と共に「変更前の結果」に移し、現在の有効な結果にしない |

検証成功は `performed === true` かつ `valid === true` が必要。
成功状態と矛盾する応答は実行失敗にする。古い結果で現在の需要充足を計算しない。
無解や未確定では配置人数0・全担当削除・不足人数の推定を表示しない。
比較元の有効な解と変更条件は残し、現在側には状態を表示する。
両方に有効な解があっても「変更を最小化した結果」と説明しない。

シナリオ切替と復元は「変更した条件と比較結果を置き換えます」と操作付近に明記し、
条件・結果・比較元・ガイド位置を一括してリセットして初期計算へ戻す。
変更がある場合のシナリオ切替は標準の確認ダイアログで確定し、取消時は元の選択を保持する。
実行世代番号は単調増加させ、取得失敗・タイムアウトで失効させる。
ボタン無効化を通り抜けた古い応答も、世代番号と `request_id` が合わなければ採用しない。

## ローカル実行入口

リポジトリ内の `demo/` に `server.py` / `index.html` / `app.js` / `style.css` を置く。
サンプルは `examples/playground/` を正本としてサーバーから読む。パッケージと既存 CLI の入口は変更しない。
以下の起動契約を #28 で実装した。新しい環境では最初に Git と uv を導入し、リポジトリを clone する。

```sh
uv python install
uv sync --locked
uv run --locked python demo/server.py
# http://127.0.0.1:8765 をブラウザーで開く。終了は Ctrl+C。
```

バインドは `127.0.0.1` 固定、ポートは8765、必要時だけ `--port` で変更する。
自動で外部公開・ブラウザー起動・パッケージ追加を行わない。OR-Tools はこのデモだけなら不要。
既存開発・CI は `--extra cp-sat` を維持する。

| 経路 | 契約 |
| --- | --- |
| `GET /` / `/app.js` / `/style.css` | 明示した3ファイルだけを返す。リポジトリ全体の配信やディレクトリ一覧は禁止 |
| `GET /samples/lunch.json` / `/samples/scenarios.json` | 固定サンプルと操作定義。期待値を成功結果として返さない |
| `POST /solve` | 本文に確定 Request を直接渡し、JSON Response を返す |

`POST` は `application/json`、UTF-8、本文64 KiB以下、明示 `Content-Length` に限定する。
転送エンコーディング、想定外パス・メソッド、許可しない `Host` / `Origin` は拒否する。
`Host` は実際に起動した `127.0.0.1:<port>`、`Origin` はその HTTP origin または未指定に限定し、CORS は許可しない。
読み取りのタイムアウトを設定し、同時の `solve` は1件、重複時は HTTP 503 と再試行可能な `BUSY` を返す。
架空データでもラベルは `textContent` で表示し、コード実行・`innerHTML`・本文のアクセスログ出力をしない。

エンジンまで渡した入力は状態によらず HTTP 200 / 未加工 Response とする（`INVALID_INPUT` を含む）。
読み取り不正・デモ範囲外は400、過大本文は413、メディア型不正は415、
Host / Origin 不正は403、実行入口自体の予期しない障害は500とする。
入口独自の失敗は `{error: {code, message, json_pointer}}` とし、エンジンの Response を装わない。
`json_pointer` は対象欄がないとき `null`。非200・通信例外・Response の矛盾をそれぞれ扱う。

ブラウザーは15秒で待機を打ち切り、古い応答を失効させる。
これはサーバー処理の停止保証ではなく、5秒はモデル準備後の探索予算である。
固定規模のローカルデモで開始し、総時間の保証・強制キャンセル・外部公開が必要になれば別途設計する。

標準機能の確認元（2026-10-06）:
[Python HTTP server](https://docs.python.org/3.14/library/http.server.html)、
[HTML 数値入力](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/number)、
[Fetch API](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)。
`http.server` はローカル試用の選択であり、production サーバーとして採用した意味を持たない。

## 検証記録と引き継ぎ

2026-10-06、エンジン `1bace6f`、Python 3.14.8 / jsonschema 4.26.0 / pytest 9.1.1 で実行した。
3シナリオの初期・変更・復元と欠勤後の修正を含む10条件は、9条件が `OPTIMAL` / 独立検証成功、

## JSON からの担当配置・勤務計画

画面上部に独立した JSON 入力欄を置き、貼り付け・UTF-8 ファイル・保存済みサンプルから実計算する。
担当配置フォームの固定条件を外す代わりに、既存の契約0.1・0.2とエンジンの入力上限をそのまま適用する。
入力をフォーム用に変換せず、制約・選好・目的・履歴・勤務テンプレートなどを保持する。
JSON 入力の結果は固定フォームの比較元にはしない。

`/solve-json` は原文を `load_json` で読み、既存 `solve` に渡す。
重複キー・非有限数・不正 UTF-8 を拒否し、本文は2 MiBまでとする。
loopback・Host / Origin・静的ファイルの限定配信・同時1件の計算は `/solve` と共通である。
不正な契約・参照はエンジンの `INVALID_INPUT` と診断を保持する。
JSON の編集・読み込みで前の結果を失効させ、計算中は両方の入力を無効にする。
待機期限は11分で、サーバーの強制停止を保証しない。入力の探索予算を無断で変更しない。

検証済みの解だけを、計画のタイムゾーンで日付ごとに表示する。
担当配置と需要充足は1日分の時間枠に限定し、100人×1440枠の表を一度に描画しない。
初期表示は需要または勤務がある時間枠とし、「全時間枠を表示」でその日全体へ切り替える。
勤務計画では選択した勤務区間と休憩から「休憩」「待機」「勤務なし」を区別し、
夜勤・分割勤務も返却された勤務区間に従う。診断・目的の証明範囲・確定入力と実結果は詳細欄に残す。

[100人・30日・30分刻みのサンプル](../examples/playground/roster-100-30.json)は、
2026-10-01から30日、2役割、1440時間枠、3000勤務候補、探索予算30秒の架空入力である。
各役割50人から毎日20人を選び、昼の2枠では休憩を考慮して需要を各10人にする。
勤務量上限9000分、勤務間の休息660分、連勤上限5日を必須条件とし、勤務量を最小化する。
これらは法令・就業規則の推奨値ではない。
実計算で1200勤務・勤務量540000分の独立検証済み解を確認した。
これは実測例であり、`FEASIBLE` の勤務件数・勤務量を固定の期待値としない。
受け入れ時は元入力に対する必須条件と、返却した目的値の再計算結果を照合する。
最適性の証明や処理時間は環境・入力条件によって変わり、`FEASIBLE` と `UNKNOWN` を `OPTIMAL` に置き換えない。
