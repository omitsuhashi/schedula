# 勤務計画の利用手順

> 導入時の実装・設計記録です。本文の旧契約・旧型・当時の対応範囲は現在の通常サポートではありません。業務機能は維持し、現在の入力・候補・履歴・再計画・診断・証明は[現行契約0.15](io-contract-current.md)、APIと実行例は[Python公開API](python-api.md)を参照してください。


schedula 0.1.3 の `roster` は、出退勤・休憩を持つ有限の勤務候補から、勤務と担当配置を
同じ CP-SAT モデルで決める。[入出力契約](io-contract.md)と [ADR-0002](adr/0002-joint-roster-optimization.md)
の業務上の意味を維持する。契約版は0.1で、Schema の構造は変更していない。

## 実行

```sh
uv sync --locked --extra cp-sat
uv run --locked --extra cp-sat python -m shift_schedula solve examples/roster.json
uv run --locked --extra cp-sat python -m shift_schedula solve - < examples/roster.json
```

ライブラリも `from shift_schedula import solve` の同じ入口を使用する。
[架空の飲食店の例](../examples/roster.json)は4人・2日・30分枠で、
32候補から8勤務を選び、調理・ホール・皿洗いの厳密な需要を満たす。
選好ペナルティ60・勤務量2640分・担当切替0回の検証済み `OPTIMAL` を返す。
皿洗い担当の休憩を埋めるため、各日30分だけ技能者の皿洗いが必要になる。
目的は選好 → 勤務量 → 担当切替の順で、先に証明した最適値を維持して後段を解く。

`auto` は常に `cp_sat` を選び、`selection_reason: JOINT_ROSTER` と記録する。
明示した `cp_sat` も使用できる。`min_cost_flow` は `INVALID_INPUT`、依存不足は
`BACKEND_UNAVAILABLE` とし、必要な条件を捨てて退避しない。
状態・診断・終了コードは [担当配置の結果の判断](assignment.md#結果の判断)と共通である。

## 勤務候補と時間

- 計画期間の両端は指定 IANA タイムゾーンのローカル日付00:00にする。
- 1人・ローカル日付につき最大1候補を選ぶ。複数の候補は代替案であり、分割勤務にはしない。
- 勤務は半開区間。終業00:00は直前の日付の勤務に含める。日付をまたぐ勤務は拒否する。
- 休憩は勤務内で始業・終業に接しない、互いに重ならない区間にする。
  明示候補では複数休憩も使える。
- 休憩を含む勤務全体が勤務可能時間に収まる必要がある。接する勤務可能区間は連結して扱える。
- 担当は選ばれた勤務の休憩以外に限定する。勤務中の未担当時間は待機となる。
  需要がない時間に余分な役割担当を作らない。

秒・端数分、計画開始からの粒度のずれを拒否する。時間枠・勤務量・休息は UTC の実時間で
計算し、結果は指定タイムゾーンで表示する。時計変更で重複した時刻は、
オフセット付きの明示候補で一つの時点を指定できる。

## テンプレートの展開

`shift_candidates` と任意の `shift_templates` を合成する。
各テンプレートは対象者 × 日付 × 始業時刻 × 勤務長 × 休憩位置の直積を生成する。
`break_options` は一つの休憩位置の代替案であり、各候補に全部の休憩を入れない。
空配列は休憩なし。勤務長・休憩位置・休憩長は始業からの実時間の分数とする。
すべての勤務長と休憩位置の組合せが、勤務内の正しい休憩を表す必要がある。

| 入力 | 処理 |
| --- | --- |
| 明示候補の計画期間外・勤務可能時間外 | `INVALID_INPUT` |
| テンプレートから生成した候補の計画期間外・勤務可能時間外 | その候補を除外 |
| 不正な休憩・粒度・夜勤・参照先 | テンプレートでも `INVALID_INPUT` |
| テンプレートに指定した曖昧な始業時刻・存在しない始業時刻 | `INVALID_INPUT` |

候補IDは `tmpl.` と、テンプレートID・従業員ID・日付・始業時刻・勤務長・休憩条件の
JSON 表現の SHA-256 から生成する。入力配列の順序を変えても、同じ候補集合とIDになる。
生成候補と明示候補のIDの衝突も拒否する。候補の出力順序は従業員・開始・終了・IDで固定する。

勤務候補件数の上限は撤廃した。除外前のテンプレート直積を別件数へ制限せず、超過分を切り捨てない。
勤務可能時間外で大量に除外される入力も、この上限を超えたら展開前に拒否する。
従業員・役割・時間枠などの共通上限は [担当配置の上限](assignment.md#上限と探索時間)を参照する。
上限内の応答性能を保証するものではない。

## 計画前履歴と必須ルール

全従業員に `history` を指定する。影響する以前の勤務がない場合も、
`last_shift_end: null` と `consecutive_work_days_before_window: 0` を明示する。
不明な履歴を空履歴へ置換しない。最終勤務終了は計画開始以前とし、
終端を除いた最終勤務日が直前日なら連勤数は正、それ以前なら0にする。
最終勤務なしで正の連勤数を指定する入力も拒否する。

| ルール・目的 | 計算 |
| --- | --- |
| `max_scheduled_minutes` | 従業員ごとの選択勤務の実時間から休憩を引く。待機を含める |
| `min_rest_minutes` | 勤務終了から次の開始まで。計画前の最終勤務とも比較する |
| `max_consecutive_days` | 勤務を選んだローカル日付の連続数。履歴を引き継ぎ、休日で0に戻す |
| `max_assigned_minutes` | 実際に役割を担当した分数。待機・休憩を含めない |
| `max_role_switches` | 隣接枠で両方とも担当し、役割が変わる回数。休憩・待機を挟んだ変更は数えない |
| `scheduled_minutes` 目的 | 全従業員の勤務量の合計。休憩を除き、待機を含む |

各ルールを対象者一人ずつに適用し、同じ対象への複数のルールもすべて守る。
分数の上限・最小休息は粒度の倍数でなくても受理し、丸めずに比較する。
計画前の連勤数が上限を超えていても、計画内の最初の日を休日として連勤を切れる。

目的は空、または `preference_penalty` / `scheduled_minutes` / `role_switches` の順序付き配列。
同じ指標は重複指定しない。選好がある場合は `preference_penalty` 目的が必要である。
空目的で勤務量が最小になるとは保証しない。

## 結果の検証と最適性の範囲

独立検証器は元入力から候補を再展開し、候補ID・従業員・勤務区間・休憩の一致、
1人1日最大1勤務、選ばれた勤務内の担当、各勤務ルールと目的値を照合する。
ソルバーの候補表・選択変数・目的値は検証の正本にしない。
不正な候補、休憩中・未選択勤務への担当、ルール違反、目的値の不一致は
`INTERNAL_ERROR` / `solution: null` として公開を遮断する。`FEASIBLE` も同じ検証を通す。

`OPTIMAL` は入力された・生成された有限候補、時間粒度、必須条件、指定した目的順序の範囲での
最適性を示す。候補外の出退勤・休憩、未入力ルールや現場データの真偽の保証ではない。
試験の休憩・休息値は法令・就業規則の推奨値ではない。
探索予算は候補生成・依存読み込み・モデル構築を終えてから全目的で共有する。
上位目的未証明なら終了し、後段の時間切れでは最良の既知解と証明済みの先頭部分を保持する。
返す解の全目的値を独立に再計算し、検証成功時だけ `FEASIBLE` を返す。
モデル不正・内部障害・固定済み最適値との矛盾は `INTERNAL_ERROR` とし、解を返さない。
探索時間の記録は [入出力契約](io-contract.md#response-と呼び出し側の扱い)に従う。
勤務計画の実測は [勤務計画の検証記録](evaluations/roster.md)、
目的順序と終了状態の実測は [目的順序・終了状態の検証記録](evaluations/objectives.md)に記録する。
クリーンな wheel の隔離導入と20人・7日・560候補の架空入力による時間・メモリは
[利用入口・CI・実行評価](evaluations/runtime.md)に記録する。

## 契約0.3の不足付き勤務計画

本書の従来候補・テンプレート表現は0.1である。0.2・0.3では `segments` / `segment_options` と
`history.last_work_day` を明示し、夜勤・分割勤務・公平性・再計画を継承する。
[契約0.3](io-contract-partial.md)では勤務選択と担当配置の同時最適化を維持し、
元の需要に対する不足人分を勤務量・公平性・変更最小化より先に最小化する。
固定部分、休憩、勤務量上限、休息、連勤は必須条件のままである。

```sh
uv run --locked --extra cp-sat python -m shift_schedula solve examples/partial_roster.json > result.json
```

`PARTIAL`、不足合計30人分、勤務量90分、最小性証明済み、CLI終了コード2となる。
不足があっても他の必須条件と集計を検証できた計画を返す。固定などが成立しなければ
`INFEASIBLE`、計画を取得できなければ `UNKNOWN` とし、空計画を捏造しない。
基準計画は0.3でも完全な計画に限定する。[検証記録](evaluations/partial-plans.md)を参照する。
